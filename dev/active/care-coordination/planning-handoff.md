## 1 다음 에이전트에게

- **인터뷰는 이미 했다. 제품 정의와 범위를 처음부터 다시 묻지 않는다.** 사용자는 “이걸 다 했는데 왜 또 하냐 지금”이라고 정정했다.
- 이 문서는 새 구현 계획이 아니라 사용자와 나눈 많은 대화의 인계다. 이 입력을 읽고 Superpowers의 `writing-plans` 절차로 구체적인 계획을 작성한다.
- 계획 작성까지만 수행한다. 코드·프론트·서비스·실제 통화·배포를 지금 실행하지 않는다. 새 실행 요청이 오면 그 범위에서 구현한다.
- 확정한 내용은 다시 묻지 않는다. 기술적 사실은 직접 조사한다. 실제로 새로운 제품 선택이 발견됐을 때만 권고안·이유·대안을 제시하고 확인받는다. 여러 선택을 필요 없이 한 턴에 하나씩 길게 인터뷰하지 않는다.
- 기능 추가·축소를 임의로 결정하지 않는다. 구현 순서를 정하는 일과 범위를 줄이는 일은 다르다.
- 본문의 “직접 지시”, “전체 승인”, “후속 정정”, “권고 후보”를 구분한다. 사용자 직접 지시와 최신 정정이 앞선 에이전트 제안보다 우선한다.
- 기존 `implementation-plan.md`는 참고 보존 자료다. 작성자가 잘못 해석한 부분이 있으므로 그 파일에서 제품 정의·MVP 경계·승인 여부를 역추론하지 않는다.
- 삭제된 `hackathon-mvp-plan.md`를 복구해 조금 고치는 방식으로 재사용하지 않는다. Git 이력에 남은 해당 파일도 승인된 계획이 아니다.

## 2 가장 중요한 사용자 지시

아래는 사용자가 직접 강조한 말이다.

> “전화가, 매우 확실히 된다. 반드시 실제 작동한다.”
>
> “프론트가 매우 아름다워야 하며, 빈틈이나 슬롭이 절대 없어야 한다.”
>
> “가장 중요: 발표용 덱, 정책 제안용 제안서.”
>
> “이건 해커톤을 위한건데, 너무 세밀한 것까지 모두 할 순 없어. mvp만 나오면 돼서, 이건 과한거야.”
>
> “계획 짜던 그거는 마저 하자. 그거는 future plan으로 넣어놓게. 나중에라도 하게.”

따라서 계획은 아래 두 산출물로 분리한다.

| 산출물 | 목적 | 지켜야 할 것 |
|---|---|---|
| Future Plan | 이미 논의한 전체 제품·후속 기능을 잃지 않고 나중에 구현 | 목적·흐름·관계·선행조건·순서·완료 기준과 미결정 운영값 보존 |
| 해커톤 MVP 구현 계획 | 이번에 실제로 만들고 시연·제출할 범위를 실행 가능하게 분해 | 덱·정책 제안서 최우선, 확실한 실제 전화, 실제 데이터/행동 연결, Claude의 아름다운 프론트 |

덱과 제안서를 마지막에 급히 붙이는 부속물로 취급하지 않는다. 초반부터 전달할 주장과 제품에서 보여줄 증거를 연결한다. 해커톤 MVP의 기능 수는 줄일 수 있으나 핵심 가치와 전화·프론트·제출물 완성도를 줄이지 않는다.

## 3 제품 해석의 경계

### 3.1 처음 전달된 맥락

사용자는 지원사업·기관·이용방법 데이터망과 대시보드를 먼저 만들고, AI 확인전화가 “그래서 이 사람이 지금 받을 수 있나요?”에 필요한 남은 조건을 채우는 방향을 가져왔다. 기존 사업과 이용 경로를 연결하며 데이터망·AI·대시보드는 같은 정보를 사용한다.

사용자는 곧 다음을 명시했다.

- **사업은 딱 네 개로 고정**한다. 범용 복지 검색 플랫폼으로 넓히지 않는다.
- 데이터망·대시보드는 공개 데이터부터 만든다. 부족한 데이터는 정책 제안 때 요청하면 된다.
- AI 확인전화가 굉장히 중요한 차별점이라는 이해에 동의했다.
- 목업 데이터를 쓰더라도 현실의 기관과 사업에 맞아야 한다.

### 3.2 전체 승인받은 제품 흐름

13개 설계안을 제시했을 때 사용자가 “전체 맞아”라고 승인했다. 그 설계의 중심은 시민이 생활상의 필요를 말하면 말결이 일을 맡아 적절한 기관에 문의하고, 답변에 따라 방법과 조건을 조율하며, 결과를 시민에게 돌려주는 흐름이었다. 시민은 사업명을 먼저 알아야 하거나 화면을 조작해야 이용할 수 있는 것이 아니다.

AI는 단순 검색 결과를 읽는 역할에 머물지 않는다. 기관에 실제로 묻고 답을 처리하며, 거절·조건 변경 때 다음 경로를 이어간다. 데이터망·대시보드는 이 일을 가능하게 하고 사람이 진행을 이해·개입하는 기반이다.

### 3.3 사용자가 거절한 문장과 실패

이후 에이전트가 작성한 계획의 첫 문장은 다음이었다.

> “말결은 시민이 전화로 생활상의 어려움을 말하면 서울의 네 사업에서 지원 경로를 찾고, AI가 기관에 실제로 전화해 조건을 알아본 뒤 시민에게 다음 행동을 알려주는 제품이다. 시민의 나이·장애 유형을 고정하지 않는다.”

사용자는 “우리가 논의한거랑 정반대”, “이게 말결이야?”라고 거절하고 삭제를 지시했다. **이 문장을 승인된 제품 정의로 사용하지 않는다.**

에이전트는 시민의 일을 맡는 핵심이 ‘경로 검색·다음 행동 안내’로 축소됐다고 설명했다. 이 설명 자체도 사용자에게 새로 승인받은 제품 카피는 아니다. 특히 뒤에 제안했던 “생활지원 전화 대리인”이라는 새 한 문장을 사용자 확정 문구라고 기록하지 않는다. 이미 승인된 기능과 역할을 정확히 서술하되 새 슬로건을 정답으로 가정하지 않는다.

에이전트가 MVP 경량화 과정에서 제안한 ‘문의·안내까지만 하고 신청·예약·조율을 전부 제외’라는 경계도 자동 확정하면 안 된다. 상용 행정 연동의 복잡성과, 역할극에서 시민의 부탁을 맡아 조건을 조율하고 일을 이어가는 핵심을 구분해서 계획한다. 사용자가 전체 계획의 축소 해석을 거절했으므로 이 경계는 신중히 재구성해야 한다. 이미 정한 제품 전체를 다시 인터뷰하라는 뜻은 아니다.

## 4 승인된 13개 설계

이 절은 사용자가 “전체 맞아”라고 답한 설계의 내용이다. 이후 해커톤 경량화·역할극·Claude 전담 지시를 함께 적용한다.

| 항목 | 승인된 내용 |
|---|---|
| 1. 주인공·입구 | 도움이 필요하지만 기관에 직접 찾아가거나 문의하기 어려운 시민. 전화가 주된 입구. 특정 연령·장애 유형으로 제한하지 않음. 생활 언어에서 필요를 파악 |
| 2. 대시보드 | 지원 연결 담당자가 주 사용자. 지원망 조회와 요청 진행·기관 답변·필요한 개입. 시민은 전화만으로 이용. 별도 시민 앱·기관 포털·기관 가입을 필수로 두지 않음 |
| 3. 대표 장면 | “쌀은 있는데 밥하기 어렵고 비누도 필요하며 가지러 갈 수 없다.” 조리 어려움·식사·생필품·방문 제약을 구분. 네 사업을 한 사람에게 억지로 모두 연결하지 않음 |
| 4. 해결 지점 | 창구·준비물·절차·일정·수령 방법이 정해진 지원 연결. 허용된 범위에서 신청 의사 전달·상담 연결·일정 조율. 기관의 자격/제공 판단은 기관에 둠. 실제 제공은 후속 기록과 구분 |
| 5. 데이터 범위 | 서울의 네 사업 고정. 서울 전체 공개 목록 수집과 기관별 상세 경로 구축을 구분. 대표 지역은 공개 자료를 비교해 선정하며 전체 범위를 줄이지 않음 |
| 6. 이용자 맥락 | 지역·필요·시급성·방문/조리/연락 제약·기존 지원·희망 연락·전달 허용 내용. 필요할 때만 질문. 전체 제품은 통화가 아니라 지속되는 요청을 기억 |
| 7. AI 전화 | 문의 → 조건 조율 → 허용된 연결. 등록된 목적별 연락처 사용. 목적·전달 내용을 설명하고 동의 확보. 중요한 조건 변화는 시민 선택. 기관에도 AI와 문의 목적을 밝힘 |
| 8. 다기관 처리 | 요청 아래 필요별 진행. 식사는 유지하고 생필품만 재탐색 가능. 거절 원인을 관할·절차·일정·품목·수령 조건으로 구분. 적합한 후보부터 순차 연락, 중복 신청 방지 |
| 9. 회신 | 시민을 계속 대기시키지 않음. 접수 후 기관 연락, 시민에게 전화로 결과 회신. 결과 → 가능한 방법 → 선택/준비 → 이어갈 일. 문자 보조는 선택적 |
| 10. 정보·상태 | 사업·기관/장소·사업별 운영·이용 경로를 분리. 요청·필요·문의·답변·다음 행동 연결. 출처·답변 이력 보존, 개인별 답변 일반화 금지. 사용자에게는 행동 중심 상태 |
| 11. 시연 | 실제 시민 음성·데이터 조회·기관/질문 선택·기관 음성·답변 처리·시민 회신. 준비된 수신자 활용. 실제 공공기관 참여 실적 주장 금지. 현장 장애 대비 영상 |
| 12. 정책 제안 | 시민의 기관 간 확인·조정 부담을 줄이는 흐름. 데이터·갱신·기관 창구·문의/신청 보조 범위·사람 인계·제한 실증 요청. 수요·구매의사·협조 조사는 지금 수행하지 않음 |
| 13. 구현·검증 | 기존 ClawOps/Gemini·저장 기반 재사용 가능성 확인. 데이터/API·요청·AI·전화·화면·제출물 연결. 정상 외 거절·부재·변경·부분 해결도 검증 |

## 5 해커톤 MVP와 Future의 구분

사용자는 전체 설계가 너무 세밀하다고 지적하고 해커톤 MVP로 줄이되 기존 논의는 Future로 보존하라고 했다. 아래는 축소의 취지와 보존할 영역이다. 에이전트가 작성했다가 거절된 구체 계획의 모든 제외항목을 사용자 승인으로 간주하지 않는다.

### 5.1 MVP에서 중심에 둘 것

- 네 사업의 실제 기관·이용 경로 데이터, 사람과 AI 공통 조회.
- 생활상의 필요와 제약을 이해하는 시민 음성 대화.
- 목적에 맞는 기관·질문 선택, 실제 발신·양방향 대화·답변 처리.
- 기관 답변에 따라 일을 이어가고 시민에게 실제로 회신하는 흐름.
- 여러 필요 중 일부를 유지하고 다른 필요만 대안으로 이어가는 핵심 장면.
- 현재 요청·문의·답변·회신에 필요한 기본 저장과 중복 방지.
- 매우 아름답고 실제 기능에 연결된 Claude의 프론트.
- 처음부터 준비하는 발표 덱·정책 제안서·발표 대본·시연 증거.

### 5.2 Future로 보존할 운영 복잡성

본인 인증·계정 복구·보호자 대리권, 여러 날/통화의 자동 재개·장기 기억, 영업시간·휴일·예약·횟수 기반 자동 재연락, 담당자 배정·부분 인수·미인수 알림·자동화 복귀, 실제 기관 시스템의 행정 연동, 정교한 개인정보/원음 보존·삭제, 자동 데이터 갱신·정보 충돌 검토, 분산 큐·고동시성·자동 복구, 다국어·문자·3자 통화 등이다.

신청/예약/취소의 실제 기관 시스템 연동과 역할극 안에서 문의·조건 조율·신청 의사 전달을 보여주는 것은 같은 난도의 일이 아니다. 운영 연동을 Future로 미루는 것을 이유로 제품의 대리 수행까지 안내 수준으로 축소하지 않는다.

경제성·운영·실증 계약·기관 협약·모델 비교·OCR 등은 필요와 승인에 따라 후속 검토한다. 결제·정산·배송 운영은 승인 없이 추가하지 않는다.

### 5.3 계획 작성 방식

각 기능에 MVP / Future를 표시하고 이유·의존성·완료 기준을 붙인다. 고정 성공 사례만 통과하는 구현으로 줄이지 않는다. 단계를 순차화하거나 독립 작업을 병렬화해서 속도를 내고, 기능 범위를 바꿔야 한다면 변경 부분만 명시한다.

## 6 두 전화번호 역할극: 직접 승인

사용자는 실제 공공기관 대상 왕복 확인이 지금 어렵다는 점을 정정하며 다음 방식을 직접 허용했다.

> “내가 전화번호가 2개잖아. 그러면 1개는 어르신이 실제로 거는 롤플레잉을 하고 1개는 뭔가 푸드뱅크로 한다던가 그렇게 해서라도 해야 돼.”
>
> “mvp이고 해커톤이라서 일단 시연을 위해 허용을 시키는거야.”

| 역할 | 해야 할 실제 동작 |
|---|---|
| 번호 A: 시민 역할 | 사용자가 어르신 역할로 말결에 전화해 필요를 말함. AI 질문에 답하고 이후 회신 수신 |
| 번호 B: 기관 역할 | 사용자 또는 팀원이 푸드뱅크 등 담당자로 AI 발신을 받고 조건·방법을 답함 |
| 말결 | 시민 수신 → 기관 역할 번호로 발신·대화 → 답변 처리·요청 반영 → 시민 역할 번호로 회신 |

- 팀원 번호나 가상 번호로 기관 역할을 수행해도 된다. 실제 양방향 음성과 회신이 작동해야 한다.
- 실제 공공기관이 받아야 한다거나 협약을 확보해야 한다는 조건을 다시 붙이지 않는다.
- 역할극 방식은 승인됐다. 같은 허용을 반복해서 묻지 않는다. 실행에 필요한 정확한 번호·역할·서비스 연결 설정은 확보해야 한다.
- 번호 A/B가 개인 단말·가상 번호·서비스 번호 중 무엇인지 추측하지 않는다. 말결 기존 수신 번호·발신 기능과의 실제 연결은 기술적으로 확인한다.
- 번호 B가 여러 기관 역할을 순서대로 맡을 때도 기관 ID·사업·문의 기록을 구분한다. 공개 기관 데이터의 전화번호를 시험 번호로 덮어쓰지 않는다.
- 준비된 수신자는 허용됐지만, 녹음 재생·고정 답변·화면만 바뀌는 가짜 성공으로 실제 대화·처리를 대신하지 않는다.
- 전면에 역할극용 데이터라는 배지를 붙이지 않는다. 실제 공공기관 참여·협약·지원 제공 실적으로 주장하지 않는다.
- 전화 검증은 역할극 환경에서 반복 수행한다. health·프로세스 존재·수신 한 번만으로 전체 왕복이 된다고 하지 않는다. 정확한 반복 횟수는 엔지니어링 계획에서 정할 값이지 사용자 지정 숫자가 아니다.

## 7 프론트: Claude 전담, KRDS 필수

사용자 직접 지시:

>

최신 역할 분담을 적용한다.

- Claude: 세밀한 와이어프레임·화면 구성·디자인·프론트 구현·시각 완성도.
- Codex/다음 백엔드 계획자: 데이터·백엔드·전화·API·이벤트 계약과 다른 산출물.
- KRDS 저장소를 필수 기준으로 한다. 다른 디자인시스템을 임의 선택하지 않는다.
- Codex가 특정 화면 수·레이아웃·라우트·컴포넌트를 확정하거나 Claude의 작업을 대신하지 않는다.

- 프론트가 다른 담당이라는 이유로 전체 제품의 실제 연결을 생략하지 않는다. Claude의 화면 결과와 백엔드 사건을 함께 확인한다.
- 지원망·요청 진행이라는 기능적 내용은 승인됐다. 구체적인 화면 분할과 와이어프레임은 Claude의 영역이다.

## 8 발표 덱·정책 제안서

최우선 산출물이다. 기능 구현을 모두 마친 뒤 남는 시간에 만드는 문서가 아니다.

### 8.1 전달할 내용

시민이 여러 기관을 찾아 같은 사정을 설명하고 이용 조건을 알아봐야 하는 문제, 말결이 대신 문의하고 답변에 따라 일을 이어가는 경험, 네 사업의 실제 데이터 기반, 실제 전화와 아름다운 제품 화면, 서울시에 요청할 데이터·창구·실증 환경이 한 이야기로 연결돼야 한다.

발표 장면은 짧고 선명하게 편집해도 제품을 두 기관·두 품목으로 제한하지 않는다. 기술명·내부 상태·감사/정산 위주의 과거 문구로 제품 가치를 대체하지 않는다. 근거 없는 효능 수치·비용절감·경쟁 우위를 만들지 않는다.

### 8.2 정책 요청의 합의

| 요청할 것 | 필요한 이유 |
|---|---|
| 네 사업의 기관·창구·이용절차 데이터와 갱신 체계 | 시민에게 맞는 경로를 찾기 위해 |
| 운영 일정·제공 가능 정보 | 불필요한 문의·방문을 줄이기 위해 |
| AI 확인전화를 받을 기관 창구 | 시민 대신 조건을 알아보기 위해 |
| 동의 기반 문의·신청 보조의 허용 범위 | 확인에서 실제 지원 연결까지 이어가기 위해 |
| 해결이 막힌 요청의 사람 인계 | 기관 거절·부재 뒤에도 요청을 이어가기 위해 |
| 제한된 지역·기관의 실증 환경 | 실제 이용 성과를 확인하기 위해 |

지금은 공개 데이터로 만들고 정책 제안 때 부족한 데이터·연계 협력을 요청한다. 현재 기관 협조·구매의사·수요조사를 선행 과제로 삼지 않는다. 해당 부서·공모 형식·법령·사업 조건은 작성 시 공식 근거로 확인한다.

### 8.3 다음 계획에 구체화할 산출물

덱의 논지·장면·대본, 정책 제안서의 문제/요청/실증/측정 구조, 실제 화면·전화 증거 연결, 편집 가능한 원본과 제출 파일, 영상·실패 대비 전환, 심사 Q&A, 실제 렌더·발표 리허설을 작업으로 분해한다. 발표 시간·페이지·마감은 공식 공고에서 확인하며 이전 파일의 3분·1장·20~30명·4~8주를 사용자 확정이나 행사 규정으로 사용하지 않는다.

## 9 승인된 금지사항

사용자는 에이전트의 임의 축소·가정·싫어하는 표현을 모두 드러내라고 했고, 제시된 경계안에 “그래. 맞아. 해봐.”라고 답했다.

### 9.1 줄이거나 바꾸지 않을 것

- 네 사업을 두 사업으로, 생활 필요를 쌀·비누로, 서울 공개 목록을 대표 지역만으로 축소하지 않는다.
- 기관·사업·이용 경로 데이터망을 이름·주소·전화번호 주소록으로 대체하지 않는다.
- 대시보드를 예쁜 지도·통계만 있는 화면으로 만들지 않는다.
- AI 확인전화를 질문 생성·전화 버튼까지만 구현하고 완료라 하지 않는다.
- 한 통화 종료를 전체 요청 종료로, 한 기관 결과를 모든 필요의 성공/실패로 처리하지 않는다.
- 기존 단일 품목·고정 시민 코드가 편하다는 이유로 제품 범위를 거기에 맞추지 않는다.
- 대표 사례는 발표 예시이며 제품이 처리할 수 있는 경우의 전부가 아니다.
- 사용자의 최신 MVP 경량화 지시도 지킨다. 운영 복잡성을 Future로 분리하되 시민 일을 맡는 핵심을 안내 수준으로 축소하지 않는다.

### 9.2 전면에서 제거할 것

미확인·미검증·목업·시연용·합성 데이터·더미·가짜 및 같은 부류의 연습용·샘플·placeholder, “개념 검증 수준”, “아직 구현되지 않았습니다”, “실제 서비스가 아닙니다” 같은 자기평가·개발 설명 배지·면책 반복을 사용자 화면·AI 대사·발표 기본 흐름에 내놓지 않는다.

상태는 도움 찾기·기관에 알아보기·연락 중·답변 도착·신청 준비·다른 경로 찾기·다시 연락하기·담당자 연결처럼 실제 행동과 다음 행동으로 표현한다. “기관에 직접 문의하세요”나 “가능 여부를 알 수 없습니다”만 남기고 끝내지 않는다.

내부 근거·데이터 분류·진행 사실은 관리한다. 발신 전 연락 완료, 답변 전 기관 회신 도착, 실제로 받지 않은 승인/제공을 표시하지 않는다. 기관 응답·구현 범위를 질문받으면 정확히 답한다.

### 9.3 임의로 추가하지 않을 것

다섯 번째 사업, 범용 복지 검색, 사업성·수요·구매의사·기관 협조 조사, 경제성·운영 완성을 착수 조건으로 요구, 전 기관 재고 API, 별도 시민 앱·기관 포털·회원가입, 새 모델·공급자·프레임워크·DB, 결제·정산·배송 운영, 매 단계 동의 버튼을 임의 추가하지 않는다.

기관별 절차를 말결만의 단일 주문 절차로 바꾸지 않는다. 찾아가는 푸드마켓의 개별 가정 배달, 푸드뱅크의 개인 수령, 돌봄SOS의 즉시 상품 제공을 근거 없이 가정하지 않는다.

### 9.4 작업 방식

이미 승인한 내용을 다시 인터뷰하지 않는다. “MVP니까”, “시간상”을 이유로 기능을 몰래 빼지 않는다. 새로운 제약은 원인·영향·대안으로 보고한다. 계획 승인과 구현·발신·배포 승인을 구분한다. 테스트 통과·화면 완성·프로세스 존재를 제품 전체 완료로 확대하지 않는다.

### 10.3 후속 검증 경로

전체 설계는 신규 정상 연결, 복수 필요 부분 해결, 기관 부재/거절/조건 변경, 시민 취소/변경/재통화, 보호자/담당자 인수, 중단/재시작/중복의 여섯 경로로 검토한다. 해커톤에서 이 모든 운영 기능을 자동화하라는 뜻이 아니다. 핵심 정상·부분 해결/대안·실패 후 이어가기와 후속 기능의 경계를 계획에 표시한다.

## 11 기술 맥락과 병렬 구현

### 11.1 이 세션에서 실제 확인한 코드

저장소: `sergiobuilds/malgyeol`, 브랜치 `feat/ai-for-good-product`. 코드 관찰은 45337d8 기준이며 이후 이 세션 변경은 문서뿐이었다. 구현 시작 전에 최신 코드와 다른 작업자의 변경을 다시 확인한다.

| 위치 | 읽어서 확인한 내용 | 계획 시 주의 |
|---|---|---|
| `src/careApp.ts` | HTTP·역할 토큰·내부 agent 경로·화면 제공 | 공통 API/통화 사건 통합 위치, 현재 provider 실행을 실제 기관 통화로 착각하지 않음 |
| `src/care-support/types.ts` | 세 서비스 코드·단일 품목/기관 요청 | 네 사업·여러 필요·문의·회신 구조와 차이 있음 |

### 11.2 TDD·병렬 작업에 관한 대화

사용자는 계획 후 TDD·병렬 구현이면 빨라질지 물었다. 에이전트는 공통 데이터/API/사건 계약을 먼저 정하고 다음을 나누는 방식을 제안했다.

- 데이터 수집·정규화·조회 API.
- 현재 요청·전화·답변·회신·부분 해결.
- Claude의 KRDS 프론트.
- 발표 덱·정책 제안서.

TDD는 관할/후보·답변에 따른 상태 전이·부분 해결·중복 발신·저장 같은 핵심 로직에 집중한다. 실제 전화는 역할극 실통화로 검증하고, 프론트는 Claude의 시각 검수와 실제 API 통합으로 확인한다. 단순 문구/CSS에 구현을 그대로 복제한 테스트를 늘리지 않는다.

공통 schema·기관/요청 ID·이벤트·API 오류/멱등 계약을 먼저 맞춘다. 같은 파일을 여러 작업자가 동시에 수정하지 않는다. 발신/오디오/회신의 기술 가능성을 일찍 확인하되 지금 문서 작성 중에 통화를 실행하지 않는다. 시간 추정은 해당 위험과 남은 작업 확인 후 한다.

### 11.3 도구와 저장소 상태

- Superpowers 6.3.0이 Codex 공식 marketplace 플러그인으로 설치·enabled 확인됨. repository는 `https://github.com/obra/superpowers`.
- 설치 경로: `~/.codex/plugins/cache/openai-curated-remote/superpowers/6.3.0/`.
- `brainstorming`, `writing-plans`, `test-driven-development`, 병렬 작업·리뷰 관련 스킬 포함. 이번에는 이미 끝난 인터뷰를 재시작하지 않고 관련 스킬 지침을 읽어 계획 작성에 사용한다.
- 프로젝트 authority router는 observe-only. 브랜치 문서를 canonical master의 방향 정본이라고 주장하지 않는다.
- 문서 커밋 158b0f9의 MVP 계획은 사용자 거절로 979c15c에서 삭제됨. 그 계획의 제품 정의·축소 해석은 승인 근거가 아니다.
- 별도 Codex CLI 읽기 전용 리뷰는 sandbox 오류로 실행되지 않았다. 리뷰 통과했다고 기록하지 않는다.
- 문서 변경은 commit/push하되 사용자가 볼 링크는 **GitHub URL**로 준다. 사용자는 docs.svvys.com을 볼 수 없다고 명시했다.

- 이 문서를 전체 읽고 기존 대화의 승인·정정 우선순위를 유지한다. 제품 정의를 새로 승인받는 인터뷰로 돌아가지 않는다.

- 계획과 인계만 저장한다. 구현은 별도 실행 요청 후 시작한다.
