# 말결 전화 대리인 구현 계획

생활상의 필요를 여러 기관 요청으로 연결하고, 기관의 거절·변경 뒤에도 같은 요청을 이어가는 프로토타입의 개발 순서와 완료 조건.

## 1 범위와 승인 경계

- 제품 방향은 [작업 지도](../../../docs/MASTER-MAP.md)의 D-20260917-02를 따른다. 현재 브랜치는 observe-only이며 canonical master의 방향 정본으로 승격하지 않는다.
- 이번 산출물은 구현 계획서다. 계획의 단계·기본값은 제안이며 구현 승인이나 유료 API·실제 발신·외부 연락·운영 배포 승인을 대신하지 않는다.
- 이전 전화 복구 실행 계약의 시간 제한·자동 실행 권한을 이 계획에 승계하지 않는다.
- 최우선 산출물은 실제 전화와 합성 기관 업무함을 연결한 변경 후 재협의 시연이다. 기관 협약이나 현장 면담은 이 프로토타입 개발의 선행조건이 아니다.
- 공급망 범위는 찾아가는 푸드마켓·그냥드림·돌봄SOS·승인 협약기관으로 유지한다. 대표 시연에는 식사·생필품 2개 경로만 사용하며 나머지 사업까지 연동됐다고 주장하지 않는다.
- ClawOps·Gemini 음성은 유지한다. 첫 구현에 새 LLM·OCR 공급자·결제·새 데이터베이스·범용 에이전트 프레임워크를 추가하지 않는다.
- 자격·급여·기관의 제공 승인을 AI가 결정하지 않는다. 실제 현장 연결은 사업별 권한과 협약이 확보된 뒤다.

## 3 대표 시연과 성공 조건

합성 이용자와 기관 A(식사), B(생필품), C(생필품 대안)를 사용한다. 기관 A의 식사와 B/C의 비누는 각 사업의 사용 가능 범위가 fixture에 명시되어 있어야 한다.

| 장면 | 입력/사건 | 보여줄 결과 |
|---|---|---|
| 최초 전화 | “쌀은 있지만 밥하기 어렵고 비누도 필요해요. 가지러 갈 수 없어요.” | 식사·비누 2개 필요와 조리·방문 제약; 필요한 질문만 수행 |
| 선택 | 기관 A 식사와 B 비누의 날짜·전달 방법 확인 | 명시 승인 전 전달 0건, 승인 후 하위 요청 2건 |
| 기관 응답 | A 수락, B 제공 불가 | 식사는 유지, 비누만 재협의 필요 |
| 통화 종료·재시작 | 프로세스 재시작 후 이용자가 새 callId로 전화 | 본인 확인 뒤 같은 상위 요청 재개; 다른 이용자 기록 미노출 |
| 대안 | C의 비누는 다른 날짜에 배달 가능 | 바뀐 날짜·기관을 설명하고 이용자 선택 요청 |
| 변경 선택 | 이용자가 C 제안을 명시 확인 | B의 확정 거절을 보존하고 C에 한 번 전달; A 재전송 없음 |
| 완료 화면 | C 수락 또는 수동 응답 | 시연 종료는 두 필요의 기관 수락. 실제 제공·배송 완료와 구분 |

변형: C도 불가이면 비누는 담당자 인수 대기로 남기고 식사 진행은 유지한다. 대안 강요나 지원 완료 안내를 하지 않는다. 인수 대기와 담당자 인수 완료를 구분한다.

## 4 데이터 모델 제안

새 구조는 기존 요청을 덮어쓰지 않고 상위 묶음으로 확장한다. 명칭은 구현에서 확정하되 아래 관계를 유지한다.

| 객체 | 핵심 필드 | 규칙 |
|---|---|---|
| `SupportJourney` | journeyId, beneficiaryRef, needIds, revision | 여러 통화가 같은 요청을 참조; 사건 이력과 소유권 유지 |
| `Need` | needId, category, constraints, preferences, status | 식사·생필품 각각 진행; 전체 상태는 하위 상태에서 계산 |
| `ContextFact` | value, source, confirmedAt, validUntil | 추측/확인 구분, 일시 제약 만료, 정정·삭제 지원 |
| `ProviderOffer` | offerId, providerId, item, quantity, date, delivery, version, expiresAt | 미확인 재고는 가능으로 처리하지 않음; 제안은 예약이 아님 |
| `SelectionConsent` | journeyId, needId, offerVersion, termsDigest, expiresAt, consumedAt | 기관·품목·수량·일정·전달방법 변경 시 재확인 |
| `ProviderAttempt` | attemptId, needId, caseId, generation, dispatch/status | 기존 caseId 원장과 연결; 이전 시도·거절·취소 보존 |
| `QuotaReservation` | beneficiaryRef, programId, needId, amount, state | 사업별 단위·기간·한도 구분; 교체가 이중 차감되지 않음 |
| `OutboxTask` | taskId, type, dedupeKey, dueAt, leaseUntil, status | 기관 전달·후속 연락을 영속 큐로 처리; 결과 불명 재실행 금지 |
| `CallBinding` | callId, beneficiaryRef, journeyId, verifiedAt | callId는 인증수단이 아님; 새 통화에 이전 승인 토큰 재사용 금지 |

## 5 실행 계약과 실패 처리

### 5.1 제안 생성

- Gemini는 생활 표현을 구조화하고 질문·설명을 담당한다. 서버가 검증 가능한 schema로 받으며 알 수 없는 항목은 질문으로 남긴다.
- 첫 대안 엔진은 코드로 기관·품목·제공일·배달·확인된 이용 범위의 필수 조건을 필터링한다. 선호는 가능한 후보 사이의 순위에만 사용한다.
- 공급 정보에 없는 후보를 모델이 발명하지 못하도록 서버가 offer ID와 version을 발행한다. 자격 미확인은 승인 요청으로 보낸다.
- `말고`, `취소`는 정상 변경/취소 의도로 해석할 수 있어야 한다. 기존 위험 차단을 통째로 없애지 않고 위험과 변경이 섞인 회귀 사례를 테스트한다. 건강 상태를 의료적으로 진단하지 않는다.

### 5.2 상태와 원자성

- 필요 상태: `DRAFT → AWAITING_SELECTION → DISPATCH_PENDING → WAITING_PROVIDER → ACCEPTED`. 거절·변경은 `NEEDS_REPLAN`, 해결 불가는 `HANDOFF_PENDING`, 담당자 명시 인수는 `HUMAN_OWNED`다. 실제 제공 상태는 기관 수락 이후 별도로 기록한다.
- 선택 확인·한도 예약·기관 전달 outbox를 한 트랜잭션에 저장한다. worker는 트랜잭션 밖에서 전송하고 응답을 저장한다.
- 동일 command/event ID 재처리는 같은 결과를 돌려준다. 오래된 revision·offer version·승인 토큰은 상태를 바꾸지 않는다.
- 확정 거절이면 기존 예약을 해제하고 새 선택의 예약을 잡는다. 기존 요청이 수락됐거나 전송 결과가 불명인 경우 취소 확정/readback 전에는 대체 기관에 자동 전달하지 않는다.
- 늦게 도착한 과거 응답은 attempt generation에 기록하되 최신 선택을 덮어쓰지 않는다. 실제 중복 수락 가능성은 담당자에게 넘긴다.
- 서버 재시작 시 만료 lease는 재평가하지만 `UNKNOWN` 전송을 맹목 재시도하지 않는다. 기존 provider timeout/readback 방침을 보존한다.

구현 기본 계약:

- 첫 묶음 승인은 `bundleId + journeyRevision + offerVersion 목록 + termsDigest`에 결박한다. 한 후보라도 만료되거나 예약이 실패하면 묶음 전체를 전송 전 롤백하고 다시 설명한다. 일부만 승인하려면 새 묶음을 만든다. 이미 전달된 요청의 재협의는 해당 need만 대상으로 한다.
- `CANCEL_PENDING`은 전달 후 취소 요청, `CANCELLED`는 미전송 취소 또는 기관 취소 확정이다. `DELIVERY_UNKNOWN`은 전송 여부 불명으로 자동 대체 금지, `PAUSED`는 미전송 단계의 이용자 중단이다. 제안 만료는 `AWAITING_SELECTION`으로 돌아가 재조회한다. 전달 뒤 통화 종료는 취소가 아니다.
- 상위 상태는 `HANDOFF_PENDING/HUMAN_OWNED` 존재 시 `NEEDS_HUMAN`, 그 외 `DELIVERY_UNKNOWN` 존재 시 `UNCERTAIN`, 재협의 필요가 있으면 `NEEDS_ACTION`, 나머지는 `IN_PROGRESS`로 계산한다. 모든 필요가 기관 수락 이후 또는 명시 취소이면 `ARRANGED`, 모두 취소이면 `CANCELLED`다. `ARRANGED`는 제공 완료가 아니며 취소된 필요를 화면에서 숨기지 않는다.
- 예약은 기관 수락 이후에도 유지하고 제공 확정 시 사용량으로 이동한다. 확정 거절·제공 전 취소 확정만 해제한다. 결과 불명·중복 수락 의심 시 예약을 보수적으로 유지하고 담당자가 실제 공급·취소 근거를 기록해 조정한다. 기관별 회계 규칙이 다르면 이 합성 기본값을 현장 설정으로 대체한다.
- 담당자 인수는 revision 비교로 한 사람만 성공한다. `HUMAN_OWNED`에서 자동 전달·재협의 발신을 멈추고 기관 응답은 기록만 한다. 자동화 복귀는 담당자의 명시 해제 뒤 새 이용자 승인부터 시작한다. 수동 기관 응답은 해당 기관 역할만 기록하며 actor·시각·이전 상태를 남긴다.

### 5.3 기본값과 권한

- 시연 제안 유효시간 5분, 기관 응답 대기 60초, 연락 시도 상한 2회는 합성 테스트용 기본값이다. 운영 SLA가 아니며 fake clock으로 시험한다. 현장 설정이 없으면 실제 자동 발신은 비활성이다.
- 시연은 비밀값을 소스에 넣지 않는 사전 등록 테스트 계정과 추가 확인으로 재연결을 시험한다. 발신번호만으로 타인 요청을 조회하지 않는다. 실제 수혜자 인증 방식은 현장 전제조건이다.
- 기관은 자기 하위 요청만 조회·응답하고, 담당자는 배정된 관할 요청만 인수한다. 입력의 beneficiaryRef/providerId를 신뢰하지 않고 인증 주체에서 도출한다.
- 후보 모델·기관 텍스트의 지시문은 권한을 바꾸지 못한다. tool allowlist, 입력 크기·출력 schema, 역할 경계를 적용한다.
- 기관 대기 60초가 지나면 `HANDOFF_PENDING`으로 전환하되 전송 불명 표시와 예약은 유지한다. readback은 합성 기본값 10초 간격 최대 3회 후 자동 조회를 멈춘다. 연락 2회 소진은 사람 인수로 보낸다. 담당자 미인수는 합성 기본값 5분 뒤 supervisor 업무함에 올리되 해결됐다고 기록하지 않는다. 현장 supervisor가 지정되지 않으면 실제 자동 운영을 켜지 않는다.

| D 전화 재개 | `phone.ts`, `careApp.ts`, `scripts/clawops-care-agent.py` | Gemini 도구 연결·다중 필요·현재 요청 조회·새 통화 재개 | 실제 수신에서 두 필요 선택, 통화 종료 뒤 비누만 재협의 |
| E 업무함·시연 | 기존 `public/` 사용 경로, 관련 HTTP routes/tests | 기관 가능/변경/불가 응답, 이용자 선택과 담당자 인수 표시 | 3절 전체 흐름과 접근성·브라우저 QA. 화면 변경은 design-forge 경로 사용 |
| F 후속 발신 | `outbox.ts`, 음성 adapter, 운영 runner | 동의·시간대·횟수 제한, 전화 공급자의 발신 API 계약 확인 후 연결 | 합성 scheduler 테스트, 승인된 테스트 번호 실제 발신 1회. API 미지원이면 미완료로 남김 |
| G 운영·비용·제출 | runtime runner, tests, README/TODO/POLICY_BASIS/제출 문서 | 복구·health·백업, 비용 계측, 정책 1장과 경쟁 근거 반영 | 아래 9~11절 기준 충족; 코드·시연·정책 문구 일치 |

A~E가 첫 완료 단위다. F의 실제 발신 공급자 확인이나 현장 협약이 A~E를 막지 않는다. 국산 모델·OCR 연동은 기본 흐름과 비용 계측 뒤 독립 변경으로 수행한다. 소요시간은 D의 음성 도구 통합 난도가 확인된 뒤 산정하며 한 시간 완료를 약속하지 않는다.

기억 정정·삭제의 합성 데이터 API는 A/D에서 구현한다. 증빙 수동 등록과 원문 연결·운영 보존기간·삭제 전파는 G에 속하며 A~E 시연의 필수 범위에서 제외한다. A~E는 실제 개인정보를 사용하지 않는다.

## 7 음성 도구와 발신

Gemini에 노출할 도구는 `get_active_journey`, `update_needs`, `list_offers`, `prepare_selection`, `get_pending_changes`, `request_handoff` 정도로 제한한다. 모델이 임의 beneficiaryRef를 지정하거나 기관 제공 완료를 기록하지 못하게 한다.

첫 구현은 기존 숫자키 승인을 재사용한다. 묶음 제안의 내용을 읽은 뒤 1번으로 승인하며, 재협의는 바뀐 필요 하나만 승인한다. 음성의 단순 “네”를 곧바로 기관 전달 승인으로 취급하지 않는다. 음성 명시 동의 UX는 별도 시험 후 도입한다.

발신은 동의 목적·연락 가능 시간·철회 상태를 실행 직전에 재확인한다. 부재·음성사서함에는 민감한 생활 맥락을 남기지 않는다. 사용자 철회 시 대기 연락을 취소하되 이미 진행 중인 제공 요청까지 취소됐다고 안내하지 않는다.

24시간은 가용성 목표다. 자동 시작·모니터링·장애 인수·운영자 대응이 확보되기 전에는 보장하지 않는다. 기관 영업시간과 AI 접수 가능 시간을 따로 안내한다.

## 8 증빙·정산·개인정보

- 기부물품은 제공 품목·수량·기관 기록, 유상 돌봄은 승인·제공·청구 자료, 민간 계약은 해당 납품·청구 조건을 구분해 하위 요청에 연결한다. 지급 실행 기능은 범위 밖이다.
- 첫 시연은 합성 제공/청구 자료의 수동 등록과 원문 참조까지만 구현한다. OCR 자동 추출은 공급자 승인 뒤 붙이며 OCR 결과를 원본 또는 진위 판단으로 취급하지 않는다.
- 연락처·인증정보와 생활 맥락은 분리한다. 조회는 최소 권한, 모델 입력은 최소 맥락, 로그는 원문 발화·전화번호·토큰을 기본 제외한다. Gemini로 전달되는 음성의 외부 처리를 숨기지 않는다.
- 기억 열람·정정·삭제 및 보존기간 정책을 API와 운영 절차에 넣는다. 실제 개인정보 도입 전 암호화·백업·삭제 전파·사업별 보존기간을 확정한다. 고정 합성 이용자 구현으로 실제 인증을 대체하지 않는다.

## 9 비교·비용 측정

- 기준 구현은 Gemini 단독과 동일한 기관 정보·도구를 가진 상담 흐름이다. 말결은 지속 요청·부분 재협의 엔진을 추가한 구성으로 비교한다. 접근 권한 차이로 우위를 만들지 않는다.
- 개발용 대표 시연과 평가 사례를 분리한다. 합성 변형은 엔지니어링 시험으로만 보고하고, 현장 효과는 담당자가 별도로 제공한 비식별 사례·외부 평가 후 주장한다.
- 우선 측정: 필요·제약 파악 정확성, 필요한 재질문 수, 같은 내용 재설명 수, 기관 변경 후 요청 연결률, 불필요한 재전달, 담당자 조정시간, 음성 응답 지연 p50/p95.
- 비용은 통신·음성·텍스트 추론·OCR·서버·재시도·사람 재처리를 포함한다. 지원 연결 1건당 총비용과 실패/이관 건 비용을 함께 공개한다. 총 표본수·모델/프롬프트 버전·측정 환경도 기록한다.
- 국산 모델 비교는 이 엔진의 `대안 설명/복잡한 조합` 부분부터 진행한다. 먼저 Gemini 단독을 기준으로 하고 승인된 후보를 한 번에 하나씩 추가한다. 도구 결과·프롬프트·통화 조건을 고정하고 절감률은 측정 전 공란으로 둔다.
- 작은 모델 라우팅·캐시·재사용은 잘못된 최신 재고 재사용이나 비용 이중 계산을 막아야 한다. 공급정보 버전이 바뀌면 관련 후보 캐시를 무효화한다. 느린 추가 LLM 호출로 전화 UX가 나빠지면 채택하지 않는다.

프로토타입 합격선 제안: 3절 정상/전체 대안 불가 2개 흐름과 11절 필수 실패 시험을 모두 통과하고, 통화 재개 때 이미 확인한 초기 필요·제약을 다시 묻지 않는다. 동일 시험 환경에서 일반 응대 p95 3초, 조회 포함 제안 p95 5초를 UX 목표로 삼아 실제 수치를 보고한다. 미달 시 기능 완료와 전화 UX 미달을 구분한다. 추가 LLM은 동일 평가셋의 연결 성공률·필수 안전 조건이 기준보다 나빠지지 않고 총비용이 감소하며 이 지연 목표를 만족할 때만 채택 후보가 된다. 이 수치는 설계 목표이지 실측 성과가 아니다.

## 10 경쟁 비교와 정책 제안 작업

기억 대화 자체는 [클로바 케어콜](https://www.navercorp.com/media/pressReleasesDetail?seq=30860), 전화로 복지욕구를 파악하는 기능은 [복지부 AI 초기상담](https://www.mohw.go.kr/gallery.es?act=view&bid=0003&list_no=379414&mid=a10505000000&tag=)과 겹친다. 이 출처는 앞선 조사에서 확인한 근거이며 출시 시 최신 범위를 다시 확인한다. 경쟁 서비스에 실행 기능이 없다고 단정하지 않는다.

차별화 가설은 기관의 늦은 응답·거절 뒤에도 기존 선택과 맥락을 보존해 이용자의 조정 부담을 줄인다는 것이다. 국산 모델·OCR·여러 모델 사용만으로 독자 기술을 주장하지 않는다. 독자 구현 대상은 맥락 모델·조건 기반 조합·지속 요청·부분 재협의다.

정책 제안 1장은 사회문제 → 위 시연 → 현장 적용에 필요한 결정으로 구성한다.

| 서울시에 요청할 것 | 현장 확인 질문 | 프로토타입에서 보여줄 것 |
|---|---|---|
| 제한적 위임 | 전화 동의로 요청·변경·취소 중 어디까지 가능한가 | 선택 조건에 결박된 확인과 기관 전달 |
| 기관 참여·데이터 | 누가 품목·시간·배달 조건을 갱신하는가 | 버전 있는 공급정보와 품절 후 대안 |
| 인수 책임 | 미응답·오전달·선택 실패를 누가 인수하는가 | 대기/인수 완료가 구분된 업무함 |
| 실증환경·지원 | 자치구·기관·참여 이용자·운영 인력을 확보할 수 있는가 | 실제/합성 경계, 비용·사용성 측정 계획 |

현장 인터뷰·협약은 개발과 병행할 후속 활동이며 외부 연락은 별도 승인 후 진행한다. 협약만으로 해결되는 문제를 법적 금지나 법 개정 필요로 포장하지 않는다. README·POLICY_BASIS·제출 자료의 이전 감사 중심 표현은 G에서 함께 정렬한다.

## 11 완료 조건과 출시 경계

- A~E: 대표 시연과 실패 변형 통과, 기존 171개 테스트 회귀 유지, 새 기능 테스트 추가, `npm run verify`, `project-doctor`, 독립 코드 리뷰, 화면 변경 시 시각 QA. 합성 기관 성공을 실제 제공 성공으로 보고하지 않는다.
- 필수 실패 시험: 승인 전 전달 0, 재전송·동시 승인 중복 0, 오래된 제안 거절, 이전 기관 결과 불명에서 대체 전달 차단, 재시작 복원, 타인 조회 차단, 취소와 수락 경합, 늦은 기관 응답, 대안 전부 불가, 위험 혼합 발화.
- DB 변경 전 backup API로 일관 snapshot과 복원 시험. schema migration은 기존 원본을 보존하고 실패 시 시작을 중단한다. 롤백은 기존 데이터와 호환되는 코드로만 하며 새 snapshot을 구버전에 그대로 읽히지 않는다.
- 새 흐름은 기본 비활성 feature flag로 개발하고 합성 영역에서 먼저 켠다. 장애 시 신규 자동 전달을 막고 진행 중 요청은 readback·담당자 인수로 처리한다. 플래그를 끄는 것이 기존 제공 취소를 뜻하지 않는다.
- F와 실제 현장 실증: 공급자 발신 지원, 동의·인증·보존 계약, 운영 모니터링·인수 담당자, 실제 기관 권한 확인 후 별도 완료 판정한다. 미확보 항목이 있으면 운영 가능한 프로토타입과 현장 상용 준비를 구분한다.
- 현 단계 산출물은 이 계획서와 지도 포인터다. 구현 시작은 승인 후 A부터 직렬 진행한다.
