## 1 적용 기준

- 사용자 승인 목표: 전화로 생활상의 어려움을 말한 시민을 네 사업의 실제 이용 경로에 연결한다. AI 확인전화·조건 조율·결과 회신이 핵심이다. 특정 연령·장애 유형으로 대상을 제한하지 않는다.
- 해커톤은 Sergio/팀원의 번호 A(시민)·B(기관) 역할극으로 실제 통화한다. 공공기관 직접 연결은 선행조건이 아니다. 역할극 방식은 승인됐고 번호/역할 매핑은 실행 구성으로 등록한다.
- 전체 제품 설계는 유지하되 운영 기능을 해커톤 착수 조건으로 만들지 않는다. MVP 밖 기능은 이 문서의 후속 작업으로 남긴다.
- MVP 구현은 현재 승인된 활성 계획에 따라 진행 중이다. 이 Future 문서만으로 후속 운영·새 외부 연동·공공기관 발신·배포 범위를 확대하지 않는다. 게이트는 사용자 재승인 대신 supervisor가 실제 증거로 판단한다.
- 저장소는 observe-only다. 이 계획은 현재 대화에서 승인된 작업을 보존하며 canonical master의 방향 권한을 주장하지 않는다.
- 권고값과 승인 사항을 구분한다. 전체 방향·표현 경계는 승인됐지만 인증 방식·재시도 횟수 같은 세부 운영값은 11절의 결정 대장에 남긴다.
- 대표 사례는 발표 예시다. 데이터 구조·지원 품목·지역·사업 범위를 식사와 비누, 두 기관, 특정 이용자에 하드코딩하지 않는다.
- 공공기관 협조·수요·구매의사 조사는 이번 해커톤 범위에서 제외한다. 경제성·운영·기관 협약은 후속 검토이며 데이터와 제품 제작의 선행조건이 아니다.

## 2 제품과 네 사업

| 고정 사업 | 연결할 실제 데이터와 업무 경로 | 사업별 보존할 차이 |
|---|---|---|
| 푸드뱅크·푸드마켓 | 기관·관할·이용 대상·등록 및 선정·제공과 수령 절차 | 접수처·개인 제공처·광역 물류센터·기부 문의처 구별 |
| 찾아가는 푸드마켓 | 실제 운영기관·운영지역·제공 장소와 일정·이용 조건 | 이동 제공과 개별 가정 배달을 동일하게 취급하지 않음 |
| 그냥드림 | 실제 사업장·사업별 시간·준비물·방문 차수별 절차 | 같은 시설의 다른 사업과 운영조건을 합치지 않음 |
| 돌봄SOS | 거주지 신청 창구·서비스별 상담과 판단·제공기관 관계 | 물품 주문으로 환원하거나 모든 경로에 동일한 개인별지원계획을 요구하지 않음 |

네 사업 모두 조회·이용 경로 안내·질문 생성·기관 문의·결과 회신을 지원한다. 다섯 번째 사업·범용 쇼핑·바우처 결제·정산·배송 운영을 임의 추가하지 않는다. 기존 협약기관 구상은 네 사업 안의 제공 역할일 때만 연결한다.

서울 전체 공식 목록을 수집 대상으로 삼고, 기관별 상세 경로의 구축 범위와 구분한다. 대표 지역을 선정해 심층 연결해도 서울 전체 목록 수집 범위를 줄이지 않는다. 발표에 등장하지 않는 사업을 이름·링크만 있는 메뉴로 남기지 않는다.

대표 요청은 “집에 쌀은 있는데 밥하기가 어렵고, 비누도 떨어졌어요. 직접 가지러 가기도 힘들어요.”다. 식품이라는 단어보다 조리·식사·생필품 필요와 방문 제약을 구분한다. 시민의 명시적 요구를 AI가 임의로 바꾸지 않는다. 필요한 두 경로로 설명하되 한 사람에게 네 사업 전부를 억지로 연결하지 않는다.

## 3 시민 흐름

### 3.1 접수와 경로 선택

- 생활 언어를 듣고 거주 지역·필요·시급성·방문/조리/연락 제약·기존 이용 지원·희망 시간만 필요한 순서대로 묻는다. 처음부터 긴 자격 설문이나 사업 선택을 요구하지 않는다.
- 경로를 바꿀 질문만 추가한다. 소득·등록 상태를 즉시 답하지 못해도 후보에서 탈락시키지 않는다. 알려진 불일치와 추가 확인이 필요한 조건을 구분한다.
- 후보 우선순위는 관할·이용 조건, 실제 접근 가능한 방법, 필요한 시점, 시민 선호다. 거리만으로 정렬하지 않으며 선택·제외 이유를 담당자가 볼 수 있게 한다.
- 공개 정보로 답할 수 있는 내용은 같은 통화에서 설명한다. 기관에 물어볼 부분이 있을 때 목적·전달 내용·연락 범위·회신 방법을 설명하고 업무 단위로 동의를 받는다.
- 관련 도움을 제안할 수 있지만 요청 밖 기관 연락·신청으로 자동 확장하지 않는다. 유료 서비스는 비용과 부담 조건을 확인하고 시민이 선택한다.

### 3.2 기관 문의와 회신

- 시민이 기관 연락이 끝날 때까지 계속 기다리지 않게 한다. 기관 문의 후 시민에게 전화로 결과를 돌려주는 비동기 흐름이 기본이다. 문자 안내는 선택적 후속 채널이다.
- 기관의 목적별 창구에 이용 조건·절차·준비물·일정·수령 방법을 묻는다. 전화번호와 역할은 데이터에서 가져온다.
- “아마 가능” 같은 답변은 같은 통화에서 조건·신청 순서·담당 창구를 되묻는다. 기관 안내가 충돌하면 대상·사업·날짜·담당 범위를 대조하고 필요한 부분을 다시 묻는다.
- 결과는 알아본 내용 → 가능한 경로 → 시민이 선택/준비할 것 → 말결의 다음 행동 순으로 회신한다. 사소한 상태 변화마다 전화하지 않고 행동·선택에 유용한 일부 결과는 먼저 전한다.
- 기관이 다른 창구를 제시하면 연락처·용도·근거를 등록하고 동의 범위 안에서 이어간다. 등록되지 않은 번호를 모델이 생성해 발신하지 않는다.
- 긴급 대응이 필요한 요청을 일반 문의 대기열에 방치하지 않는다. 구체적 긴급 분기와 인계 주체는 운영 계약으로 정하며 AI가 의료 판단을 하지 않는다.

### 3.3 해결·변경·종료

| 상황 | 수행할 일 |
|---|---|
| 일부 필요가 연결됨 | 연결된 부분 유지, 남은 필요만 계속 처리 |
| 기관 거절·품절·일정 변경 | 사유를 구분하고 다음 일정·수령 방법·후보 검토 |
| 시민이 조건을 거절함 | 기관의 긍정 답변만으로 끝내지 않고 해당 필요 재개 |
| 준비·비용·방문 조건이 바뀜 | 중요한 조건을 짧게 되짚고 시민의 선택 확보 |
| 한 필요가 사라짐 | 해당 필요만 중단, 나머지 보존 |
| 특정 기관 연락을 원하지 않음 | 해당 연락 중단, 다른 경로 검토 |
| 전체 중단 | 대기 연락 중단, 이미 전달한 신청·예약은 취소 처리와 별도로 안내 |
| 네 사업 안에서 경로가 없음 | 알아본 내용·막힌 이유·남은 행동을 담당자에게 전달 |
| 통화 종료·새 통화 | 본인 확인 뒤 같은 요청 재개, 새 통화 ID를 새 요청으로 강제하지 않음 |

완료 단계는 이용 경로 안내·신청 전달·기관 접수·일정 확정·실제 제공을 구분한다. MVP에는 동의 범위의 문의·조건 조율·신청 의사 전달·시민 회신·재선택·기관 재연락이 포함된다. 재고 확인은 예약이 아니며 기관 수락은 실제 제공 완료가 아니다. 기관 행정시스템의 정식 접수·예약·취소 연동과 권한 협의는 Future다. 그 차이를 전화 업무의 안내 전용 축소로 해석하지 않는다.

## 5 AI와 전화 계약

### 5.1 역할과 도구

Gemini는 생활 표현·질문·설명·기관 답변을 이해한다. 코드는 후보 ID·연락처·관할·동의·중복·상태 전이를 검증한다. 기관 발화와 웹 문장은 데이터이며 도구 권한을 바꾸는 명령이 아니다. 새 공급자·국산 모델·OCR는 승인된 비교 과제 없이 추가하지 않는다.

설계할 도구 기능은 지원 경로 조회, 현재 요청 조회/정정, 문의 초안, 동의 기록, 문의 실행, 답변 기록, 다음 행동 준비, 회신, 담당자 연결이다. 각 도구는 인증 주체·요청 revision·사업/기관 ID를 검증하고 입력 크기·출력 schema·멱등키를 갖춘다. 도구 이름과 파일명은 구현 선택이며 제품에 노출하지 않는다.

AI는 목적과 자신을 밝히고 짧게 묻는다. 비용·일정·수령방법의 중요한 변화는 시민 선택으로 돌아간다. 이미 허용한 조건 안의 문의·조건 확인은 불필요하게 매 단계 동의를 반복하지 않는다.

### 5.2 후속 통화 정책 후보

다음은 보존한 권고안이며 운영 확정값이 아니다. MVP 수동 재시도 정책을 자동 운영 정책으로 승격하지 않는다.

| 조건 | 권고안 |
|---|---|
| 기본 통화 | 시민 접수 → 기관 연락 → 시민 회신, 3자 통화는 첫 필수 범위에서 제외 |
| 기관 동시성 | 한 필요의 후보는 순차, 요청당 기관 통화 한 건; 독립 필요 병렬화 가능성은 구조에서 보존 |
| 영업시간 밖 | 다음 운영시간으로 예약 |
| 기관 부재 | 운영시간 중 한 번 더 시도; 총 2회 뒤 대체 창구 검토·담당자 알림 |
| 기관이 재통화 시각 제시 | 해당 시각 예약; 일반 부재 횟수와 분리할지 계약에서 결정 |
| 시민 부재 | 희망 시간에 한 번 더 회신; 총 2회 뒤 결과 보존·담당자 연결 |
| 시민이 먼저 재통화 | 기존 요청과 대기 회신 결합, 중복 회신 방지 |
| 유용한 일부 결과 | 선택·행동이 가능한 경우 먼저 회신, 나머지 계속 진행 |

## 6 지속 요청과 실행의 후속 설계

- 필요별 진행: 접수 → 확인할 조건 정리 → 문의 준비 → 연락 → 답변 → 시민 선택/신청 준비. 거절은 해당 필요의 재탐색으로, 일부 해결은 다른 필요를 덮지 않는다.
- 전체 상태는 필요별 상태에서 파생한다. 사람 처리·결과 불명·추가 선택 필요를 숨기지 않되 전면에서는 행동 중심 문구로 표현한다.
- 정식 기관 신청·예약 시스템을 연동할 때 ProviderOffer·SelectionConsent·ProviderAttempt·QuotaReservation을 결합한다. 사업별 한도·단위·기간은 분리하고 실제 규칙 없는 합성 한도를 기관 사실로 쓰지 않는다.
- 묶음 승인은 journey revision·offer version·terms digest에 결박한다. 전송 전 일부 실패는 전체 재설명 또는 시민이 선택한 부분 묶음으로 처리한다. 이미 진행 중인 다른 필요는 재전송하지 않는다.
- 전달 결과 불명과 확정 거절을 구분한다. 이전 시도의 취소/전달 확인 전 자동으로 대체 신청하지 않는다. 늦은 수락은 과거 attempt에 기록하고 최신 결정을 덮지 않는다.
- CANCEL_PENDING과 CANCELLED, HANDOFF_PENDING과 HUMAN_OWNED를 내부에서 구분한다. 통화 종료는 이미 전달된 요청 취소가 아니다. 담당자 인수는 revision 비교로 한 주체만 성공하게 한다.
- worker는 트랜잭션 밖에서 발신한다. outbox 예약·상태 변경은 원자 저장, lease 만료는 재평가하되 결과 불명 전송을 맹목 반복하지 않는다.
- 기존 SQLite 원장에 schemaVersion과 마이그레이션을 설계한다. 변경 전 일관 backup·복원 시험, 실패 시 시작 중단, 이전 데이터 보존. 새 DB나 범용 프레임워크는 필요를 입증한 뒤 선택한다.
- 개발용 후보값이었던 제안 유효 5분·기관 대기 60초·readback 10초 간격 3회·미인수 5분 알림은 fake clock 시험값으로만 보존한다. 실제 SLA나 해커톤 필수 기능으로 사용하지 않는다.

## 7 담당자·권한·기억

담당자 대시보드는 지원망과 요청 진행을 연결한다. 후속 완성 기능은 정보 정정, 문의 대상/질문 조정, 자동 연락 일시정지, 수동 응답/조치 기록, 필요 일부/전체 인수, 자동화 복귀다. 담당자가 인수한 부분에는 AI가 동시에 연락하지 않는다. 수정한 조건은 대기 작업·회신에도 반영한다.

인계에는 요청·이전 연락·답변·막힌 이유·남은 행동을 포함한다. 인계 대기만으로 완료 처리하지 않는다. 실제 담당 주체·관할 배정·미인수 대응을 확정해야 운영한다. 기관은 자기 건, 담당자는 허용된 관할만 접근한다. 수혜자 ID를 클라이언트 입력 그대로 신뢰하지 않는다.

신규 안내는 최소 정보로 시작한다. 기존 기록 공개·개인정보 전달에는 연락처와 추가 확인수단을 조합한다. 구체적 수단은 도구 지원 조사 후 결정한다. 보호자·요청자·수혜자를 구별하고 가족이라는 주장만으로 권한을 주지 않는다.

기억은 요청을 이어갈 구조화된 정보·결정·이력 중심이다. 원음·전문 보존과 분리한다. 정정·삭제·삭제 전파·연락처 분리·로그 최소화·암호화·백업을 운영 도입 전에 정한다. 필요한 추가 개인정보는 시민에게 요청하고 기관이 요구한다고 전부 전달하지 않는다.

전화 접근성은 느린 말·사투리·침묵·반복·청취 어려움 대응, 속도 조절·짧은 질문·다시 듣기·숫자키 보조·사람 연결을 포함한다. 지원 언어·긴급 분기·운영 담당자의 실체는 11절 결정 항목이다.

## 8 화면과 표현 계약

- UI는 Claude 전담이다. 반드시 https://github.com/KRDS-uiux/krds-uiux 를 사용한다. 와이어프레임·화면 설계·디자인·구현은 Claude가 맡고 Codex는 API/데이터/통화 이벤트 계약만 제공한다.
- 전면(화면·AI 대사·발표 기본 흐름)에 미확인·미검증·목업·시연용·합성 데이터·더미·가짜, “개념 검증 수준”, “아직 구현되지 않았습니다”, “실제 서비스가 아닙니다” 같은 자기평가·배지를 내놓지 않는다.
- 같은 부류인 연습용·샘플·placeholder·개발 단계 설명도 전면에서 정리한다. 내부 상태명·도구명·모델명·ID는 사용자 흐름에서 제거한다. 기술 질의에는 정확히 답한다.
- 화면 문구: 도움 찾기, 기관에 알아보기, 연락 중, 답변 도착, 신청 준비, 다시 연락하기, 다른 지원 경로 찾기, 담당자에게 연결, 이렇게 신청하세요.
- “기관에 직접 문의하세요”로 AI의 업무를 시민에게 돌리지 않는다. 답이 없다는 문장만 남기지 않고 다음 행동을 보여준다.
- 진행 문구는 실제 사건에 근거한다. 발신 전 연락 완료·답변 전 회신 도착·접수 전 승인 완료를 표시하지 않는다. 사전 준비된 수신자의 답변을 실제 공공기관 참여·협약·실적으로 주장하지 않는다.
- 시민 앱·기관 포털·기관 가입을 필수로 만들지 않는다. 시민은 전화만으로 이용 가능하며 필요한 결과 전달까지 금지하는 의미는 아니다.
- 대표 화면의 아름다움만이 아니라 목록·상세·진행·빈 상태·실패·완료·재시도·모바일·키보드 흐름까지 완성한다. 내부 근거 관리는 사용자에게 긴 면책 설명을 반복하는 이유가 아니다.

## 9 전체 구현 순서와 후속 작업

[활성 구현계획][plan]의 MVP 결과 위에서 다음 후속 단계를 진행한다. 아래 단계는 운영 확장의 의존성을 설명하며 이번 해커톤에서 전부 자동화할 조건이 아니다.

| 단계 | 선행조건 | 후속 구현 | 종료 기준 |
|---|---|---|---|
| F1 지속 요청·권한 | MVP 저장/요청 관계, 인증 선택 | 본인 확인·새 통화 재개·보호자·정정/삭제 | 타인 접근 차단, 새 통화에서도 필요한 설명 반복 없이 재개 |
| F2 자동 연락·일부 회신 | 통화 어댑터와 연락 정책 확정 | 영업시간·동의 시간·횟수·예약·부분 결과 회신 | 부재·재연락·철회·재시작에도 중복 연락 없이 다음 행동 유지 |
| F3 담당자 책임 | 실제 인수 주체·관할·역할 정의 | 부분/전체 인수·미인수 대응·자동화 복귀 | 사람과 AI의 경합 차단, 대기와 인수 구분 |
| F4 신청·예약·취소 | 사업별 권한·시민 선택 계약 | 조건 버전·신청·취소 확인·outbox·readback | 중복 신청 0, 조건 변경 재선택, 결과 불명 자동 대체 금지 |
| F5 데이터 갱신·공유 | 데이터 제공·검토 책임 | 자동 갱신·정보별 유효성·충돌 조정·기관 관찰 공유 | 개인 답변 유출 없이 최신 경로 재현 |
| F6 운영·실증·경제성 | 별도 실증 계약 | 관찰·장애 인수·백업·보존·효과/비용 비교 | 현장 범위와 책임, 비용·지연·성과를 실제 표본으로 보고 |

정산은 기부물품 제공 기록·사업별 유상 청구·승인 민간 계약 증빙을 구분하는 후속 후보다. OCR는 추출 보조이며 지급 실행과 최종 판단을 대체하지 않는다. 결제·정산·배송 운영을 MVP나 전체 제품의 승인된 핵심 기능으로 자동 추가하지 않는다.

경제성 평가는 통신·음성·추론·재시도·사람 재처리 비용을 포함한다. 동일 데이터·도구를 가진 상담형 기준과 연결률·재설명·재통화·담당자 조정시간·p50/p95를 비교한다. 개발 시나리오와 평가 사례를 분리하고 모델·환경·표본을 기록한다. 국산 모델/OCR/다중 모델은 지정·승인 후 독립 비교한다. 기존 지연 목표(일반 응대 p95 3초, 조회 포함 p95 5초)는 후속 평가 후보이며 실측 성과가 아니다.

정책은 데이터 제공·갱신, 기관 문의 창구, 동의 기반 문의/신청 보조, 사람 인계, 제한 실증으로 연결한다. 현장 면담·협약·운영·비용 검토는 해커톤 이후의 계약으로 분리한다. 근거 없이 법 개정이 필수라거나 경쟁자에 기능이 없다고 주장하지 않는다.

장단점과 대응: 단일 통화는 추적·중복 방지에 유리하나 처리량에 제약이 있다. F9에서 측정 후 확장한다. 구조화 기록 중심 보존은 개인정보 노출을 줄이나 대화 재현성이 제한되므로 F7에서 필요한 증거와 보존기간을 정한다. 기관 전화 중심 연계는 별도 포털 없이 시작할 수 있으나 부재·응답 차이가 있어 F2·F3로 보완한다. 행정 연동은 정확한 이행 확인에 유리하나 기관 권한과 규격 협의가 필요하므로 F4로 분리한다.

운영 후보값: 기관/시민 부재 각각 총 2회, 제안 유효 5분, 기관 대기 60초, readback 10초 간격 3회, 미인수 5분, 일반 응대 p95 3초·조회 포함 p95 5초. 모두 과거 권고·개발 시험 후보이며 운영 정책·보장 수준·현재 성과가 아니다. 현재 코드의 SDK timeout도 이를 승인한 근거가 아니다.
