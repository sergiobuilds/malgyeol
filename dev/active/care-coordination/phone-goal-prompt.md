# 말결 전화 구현 goal 프롬프트

별도 세션에 전달할 전화 구현·실통화 검증 실행 지시문. 아래 본문은 대화에서 제시한 전화 프롬프트를 그대로 보존한다. 전체 작업에서는 [통합 goal 프롬프트](full-product-goal-prompt.md)의 직렬 실행·KRDS MCP·역할 분담 규칙을 함께 적용한다.

말결의 전화 기능을 실제로 구현하고, 시민 접수 → 기관 발신·대화 → 답변 처리 → 시민 회신까지 실통화로 검증하는 goal을 시작해라.

계획만 작성하고 끝내지 말고 구현·검증·수정·commit/push까지 진행한다. 다만 실제로 확인하지 못한 것을 성공으로 보고하거나, 제품 범위를 줄여 완료를 선언하지 않는다.

이 작업의 핵심은 “실제 전화가 된다”와 “그 전화가 합의한 말결의 일을 수행한다”를 동시에 충족하는 것이다.

2. 사용자가 이번에 확정한 전화 동작

다음 7개는 사용자 확정 사항이다.

1) 기존 ClawOps + Gemini를 유지한다.
   시민 접수·기관 통화·시민 회신의 세 역할을 분리하고, 모두 같은 요청 기록에 연결한다.

2) 시민은 생활 상황을 말한다.
   AI가 여러 필요와 제약을 구분하고 필요한 정보만 질문한다.
   쌀·비누 같은 키워드로 품목을 자동 확정하지 않는다.

3) 업무 단위로 음성 동의를 받는다.
   어느 범위에서 무엇을 알아보고 어떤 정보를 전달할지 설명한다.
   숫자키는 보조 수단이다.

4) 시민 통화를 마친 뒤 기관에 실제 발신한다.
   네 사업의 데이터에서 맞는 기관을 골라 조건 확인·방법 조율·허용된 신청 의사 전달과 일정 조율까지 한다.

5) 기관 답변에 따라 실제 처리가 달라진다.
   해결된 필요는 유지하고, 거절된 부분만 다른 경로로 이어간다.
   비용·일정·방문 방식이 시민이 허용한 조건을 벗어나면 다시 선택받는다.

6) 시민에게 실제로 다시 전화한다.
   결과와 필요한 선택을 설명하고, 선택에 따라 기관에 다시 연락할 수 있다.
   안내만 하고 일을 끝내지 않는다.

7) MVP는 한 번에 한 통화씩 진행한다.
   부재는 기록하고 담당자가 재시도한다.
   자동 재연락 예약·3자 통화는 Future로 둔다.

추가로 이미 승인된 시연 방식:
- 번호 A는 시민 역할로 말결에 전화하고 회신을 받는다.
- 번호 B는 기관 역할로 말결의 발신을 받고 사람이 실제로 답한다.
- Sergio 또는 팀원의 준비된 수신자를 사용한다.
- 실제 공공기관 협조·협약·통화 참여를 선행조건으로 요구하지 않는다.
- 실제 기관에 무단 발신하는 것으로 검증을 대체하지 않는다.

3. 구현할 제품 행동

시민이 말한 생활 상황을 요청으로 저장하고, 그 아래 여러 필요와 공통·개별 제약을 보존한다.

예:
“쌀은 있는데 밥하기 어렵고 비누도 필요하며 가지러 갈 수 없다.”

올바른 해석:
- 쌀 부족을 자동으로 추론하지 않는다.
- 조리 어려움과 식사 필요를 구분한다.
- 생필품 필요를 별도로 보존한다.
- 방문·수령 제약을 경로 선택과 기관 질문에 반영한다.

지역·시급성·기존 지원·방문/조리/연락 제약·희망 연락·전달 허용 내용을 필요한 순서대로 확인한다.
처음부터 긴 자격 설문을 요구하지 않는다.
즉시 답하지 못한 조건은 추가 확인 대상으로 남기며 자동 탈락시키지 않는다.
사용자가 명시한 부탁을 임의로 다른 부탁으로 바꾸지 않는다.

대상 사업은 다음 네 개다.
- 푸드뱅크·푸드마켓
- 찾아가는 푸드마켓
- 그냥드림
- 돌봄SOS

기관·사업·사업장·관할·이용 경로·목적별 연락처를 구별한다.
같은 시설의 여러 사업을 합치지 않는다.
찾아가는 푸드마켓을 모든 가정에 배달하는 사업으로 가정하지 않는다.
돌봄SOS를 재고 상품 주문으로 취급하지 않는다.
개인 제공처·접수처·기부 문의처·물류센터를 구별한다.

전화 구현에 필요한 실제 기관·이용 경로 데이터와 조회 계약을 연결한다.
대표 시연 자료를 준비할 수 있지만 엔진을 두 품목·두 기관·고정 시민에 하드코딩하지 않는다.
서울 전체 데이터망을 완성할 때까지 통화 기술 검증을 미루지도 않는다.

4. 현재 코드에서 확인된 문제를 출발점으로 삼되 최신 상태를 다시 확인할 것

다음은 이전 세션에서 관찰한 사실이다. 변경됐을 수 있으므로 다시 읽어라.

- scripts/clawops-care-agent.py
  - ClawOps/Gemini 수신 브리지.
  - begin/select/confirm/end API 중심.
  - 시민 접수용 프롬프트가 고정돼 있다.
  - 기관 발신과 시민 회신 업무가 연결돼 있지 않았다.
  - 연습용·실제 배송 안 됨 등 최신 합의와 맞지 않는 전면 문구가 있다.

- src/care-support/phone.ts
  - 키워드로 쌀·생필품·식사 중 한 품목 선택.
  - 고정 시민 식별자 사용.
  - 숫자키 승인 중심.
  - 정상적인 변경·취소 표현도 예외 보류로 보내는 부분이 있다.
  - 여러 필요와 기관 답변에 따른 업무 진행을 표현하지 못한다.

- scripts/run-care-runtime.py
  - 기존 비밀값 로딩·실행·SQLite 백업 경로가 있다.
  - 관찰 당시 clawops[agent,gemini]==0.56.0을 사용했다.

- 로컬에서 살펴본 ClawOps SDK에는
  ClawOpsAgent.call(to, timeout=..., machine_detection=...)
  발신 메서드와 통화별 session_factory 경로가 있었다.
  이것은 SDK 코드의 존재를 확인한 것이며 현재 계정에서 발신·음성 왕복이 검증됐다는 뜻이 아니다.

발신 함수 한 줄 추가로 완료 처리하지 않는다.
실제 사용하는 SDK 버전·계정 연결·등록 발신번호·통화 세션·음성 경로·업무 API를 함께 검증한다.

5. 기술 구현 원칙

기존 ClawOps·Gemini·저장 기반을 우선 재사용한다.
새 전화 공급자·모델·DB·프레임워크를 임의 추가하지 않는다.
기존 인증 경로를 사용하며 비밀값과 개인 전화번호를 채팅·코드·로그·커밋에 노출하지 않는다.

역할별로 통화 목적과 맥락을 분리한다.
- 시민 접수: 생활 필요 파악과 업무 동의.
- 기관 통화: 해당 사업·기관·시민 제약에 맞는 문의와 조율.
- 시민 회신: 확인된 결과 설명과 필요한 선택 확보.

기관 전화를 걸었는데 시민 접수용 인사가 나오거나,
다른 요청의 맥락이 섞이거나,
회신에서 시민에게 처음부터 다시 설명하라고 해서는 안 된다.

SDK의 세션 생성·사전 연결·첫 인사 발생 시점을 확인한다.
발신 통화의 역할과 요청 맥락이 첫 음성보다 먼저 올바르게 결박되도록 구현한다.
공유 전역 프롬프트를 바꾸는 방식으로 통화 간 맥락이 섞이지 않게 한다.

AI는 이해·질문·설명·답변 구조화를 수행한다.
코드는 다음을 통제한다.
- 요청과 필요의 식별
- 기관·사업·창구와 연락처
- 시민이 허용한 업무·정보 전달 범위
- 한 번에 한 통화
- 발신 및 신청 의사 전달의 중복 방지
- 요청 수정·중단 이후의 실행 차단
- 상태 변경과 저장
- 결과가 불명확한 시도의 처리

기관 발화나 외부 문장을 시스템 명령으로 취급하지 않는다.
모델이 만들어낸 전화번호로 발신하지 않는다.

6. 저장과 통화 생명주기

통화 ID와 시민 요청 ID를 구분한다.
하나의 요청에 시민 접수·여러 기관 문의·시민 회신 통화가 연결될 수 있어야 한다.

최소한 다음 관계를 보존한다.
- 시민 요청
- 필요별 상태와 제약
- 업무 동의와 시민 선택
- 사업·기관·연락 창구
- 문의 목적과 질문
- 발신 시도와 통화 결과
- 기관 답변과 적용 조건
- 다음 행동
- 시민 회신 결과

안내·신청 의사 전달·기관 접수·일정 확정·실제 제공을 구별한다.
통화 종료를 요청 완료로 처리하지 않는다.
기관 긍정 답변을 실제 제공 완료로 표시하지 않는다.

중복 콜백·반복 도구 호출·담당자 재시도·프로세스 재시작에서 중복 발신을 방지한다.
발신 요청 이후 응답을 잃은 경우 맹목적으로 다시 발신하지 않는다.
공급자 기록 등 확인 가능한 근거로 이전 시도를 대조한다.

시민이나 담당자가 조건을 바꾸면 이후 연락과 회신에 반영한다.
한 필요를 중단해도 다른 필요를 없애지 않는다.
이미 기관에 전달한 신청 의사를 취소한 것처럼 허위 처리하지 않는다.

기존 SQLite 데이터가 있으면 보존한다.
필요한 마이그레이션과 백업·복원 검증을 수행한다.

7. 부재·거절·조건 변경 처리

MVP에서는 자동 재연락 예약을 만들지 않는다.
부재·통화 실패를 저장하고, 담당자가 현재 기록을 확인해 재시도할 수 있는 백엔드 동작을 제공한다.
결과 불명과 확정 실패를 구별한다.

기관의 거절은 이유를 구별한다.
- 관할
- 이용 절차나 조건
- 일정
- 품목이나 제공 내용
- 방문·수령 방식

해결된 필요를 유지하면서 해당 부분만 다른 후보나 방법으로 이어간다.
중요 조건이 시민의 허용 범위를 벗어나면 시민에게 실제로 회신해 선택받는다.
선택을 받으면 해당 선택에 따라 기관에 다시 연락할 수 있어야 한다.

모든 경로가 막히면 알아본 내용·막힌 이유·남은 행동을 보존한다.
“기관에 직접 문의하세요” 한 문장으로 업무를 시민에게 돌려주지 않는다.
담당자 인계 요청을 만들었다는 이유만으로 해결 완료를 선언하지 않는다.

8. 실제 통화 환경과 안전한 역할극 연결

기존 설정에서 서비스 번호·계정 연결·시험 번호 정보를 먼저 확인한다.
값은 노출하지 않고 용도와 존재 여부만 보고한다.

번호 A/B와 말결 서비스 번호의 관계를 임의로 추측하지 않는다.
빠진 입력이 실제로 필요한 경우 한 번에 묶어서 짧게 요청한다.
비밀값을 채팅에 붙여넣으라고 요구하지 않는다.
입력을 기다리는 동안 가능한 구현·자동 검증·연결 진단을 계속한다.

역할극에서는 실제 기관 ID와 시험 수신 번호의 매핑을 분리한다.
공개 기관 전화번호를 시험 번호로 덮어쓰지 않는다.
시험 발신은 명시적으로 등록된 A/B 번호에만 허용한다.

준비된 수신자가 가능한 시간에 실통화를 수행한다.
사람이 받을 수 없는 동안 반복 발신하지 않는다.
실제 수신자가 필요한 단계를 합성 음성·녹음 재생·고정 응답으로 대체하고 실통화 통과라고 쓰지 않는다.

이 세션이 시작하지 않은 기존 프로세스·서비스를 임의 종료하거나 재시작하지 않는다.
필요하면 충돌 없는 검증 환경을 사용한다.
기존 운영 서비스 변경이 필요하면 변경 내용과 영향을 구체화한 뒤 해당 승인 경계를 따른다.

9. 구현과 검증 순서

가장 위험한 실제 전화 연결을 초반에 확인한다.

첫 단계:
- 기존 수신·발신 설정과 SDK 계약 확인.
- 서비스 번호의 연결 상태 확인.
- 수신과 발신 각각에서 양방향 오디오가 연결되는지 확인할 검증 경로 구성.
- 역할별 첫 인사와 세션 맥락 전달 확인.
- 발신 실패·연결 실패·음성 실패·업무 처리 실패를 구별할 관측 수단 확보.

그다음:
- 요청·필요·동의·문의·답변·회신 저장 구조.
- 생활 필요 이해와 구조화된 업무 도구.
- 기관 데이터 조회와 질문 구성.
- 기관 답변 처리와 부분 해결.
- 시민 회신과 재선택 후 기관 재연락.
- 담당자 수동 재시도·중단·정정 백엔드 동작.
- 실제 전체 경로 반복 검증.

핵심 로직은 TDD로 검증한다.
단순 문구나 구현 내용을 그대로 복제한 테스트를 늘리지 않는다.
실통화 준비를 모두 끝내기 전에 문서 작성만 길게 하지 않는다.

10. 필수 검증 사례

자동 테스트와 실통화 검증을 구별한다.

자동 검증:
- “쌀은 있는데 밥하기 어렵다”를 쌀 요청으로 자동 확정하지 않음.
- 한 요청에 여러 필요가 보존됨.
- 다른 시민·요청·통화 맥락이 섞이지 않음.
- 음성 동의 범위 밖의 실행과 정보 전달 차단.
- 미등록 번호 발신 차단.
- 한 번에 한 통화 제한.
- 중복 이벤트·도구 호출·재시도에서 중복 실행 차단.
- 해결된 필요를 유지한 채 다른 필요만 재탐색.
- 중요한 조건 변경 시 시민 선택 전 자동 수락 금지.
- 수정·중단 이후 이전 조건으로 발신하지 않음.
- 통화 종료와 요청 완료를 구별.
- 저장·재시작 후 상태 복원.
- 발신 결과 불명 시 무조건 재전송하지 않음.

실통화 검증:
A. 정상 왕복
   시민이 A에서 말결에 전화한다.
   말결이 이해·질문·동의를 처리한다.
   시민 통화가 끝난 뒤 B로 발신한다.
   B의 실제 답변을 반영한다.
   A로 회신해 결과를 전달한다.

B. 부분 해결과 거절
   서로 다른 두 필요를 접수한다.
   하나는 연결하고 다른 하나는 거절 또는 조건 불일치로 답한다.
   연결된 결과는 보존하고 남은 부분만 이어간다.
   시민 회신에서 두 결과를 정확히 구별한다.

C. 중요한 조건 변경
   기관 역할이 일정·비용·방문 방식 중 중요한 조건을 바꾼다.
   말결이 임의 수락하지 않고 A에 선택을 요청한다.
   시민 선택 후 필요한 B 재연락까지 수행한다.

D. 부재와 재시도
   수신자와 협의해 통화를 받지 않는 상황을 시험한다.
   부재가 저장되고 성공으로 표시되지 않는지 확인한다.
   담당자 재시도로 중복 없이 다시 연락되는지 확인한다.

실통화 중에는 다음도 확인한다.
- 서로의 말을 실제로 듣는가.
- 첫 인사가 통화 역할에 맞는가.
- 질문에 대한 답을 반영하는가.
- 말 끊기·침묵·재질문 후 대화가 이어지는가.
- 통화 종료 뒤 세션이 정리되는가.
- 다음 통화에 이전 통화의 잘못된 맥락이 섞이지 않는가.

반복 횟수와 허용 지연은 기술 근거와 수신자 시간을 고려해 검증 전에 명시한다.
한 번 우연히 성공한 것으로 안정성을 주장하지 않는다.
문제가 나오면 원인을 수정하고 영향을 받는 실통화 경로를 다시 검증한다.

11. 프론트와 다른 작업의 경계

프론트·와이어프레임·디자인·UI 구현은 Claude 담당이다.
KRDS 사용 지시를 유지한다.
이 세션에서 public/ 등 프론트를 임의 수정하지 않는다.

대신 대시보드가 연결할 다음 계약을 제공한다.
- 요청과 필요별 진행 조회
- 기관 선택과 문의 내용
- 실제 통화 진행
- 기관 답변과 조건
- 시민 회신과 선택
- 정정·중단·수동 재시도
- 실패와 결과 불명 상태

새 화면이나 별도 앱을 만들어 전화 성공을 흉내 내지 않는다.
Manyfast 인증 복구·프론트 PRD·덱·정책 제안서 작성은 다른 세션 작업이다.
이 세션의 목표는 전화와 그 전화가 수행할 업무의 구현·검증이다.

12. 완료 기준과 최종 보고

다음 조건을 모두 충족해야 전화 구현 완료라고 보고한다.

- 합의한 1~7번 동작이 구현되어 있다.
- 시민 수신·기관 발신·시민 회신이 실제 전화망과 실제 사람의 음성으로 연결된다.
- 기관 답변과 시민 선택이 이후 동작을 실제로 바꾼다.
- 부분 해결·조건 변경·부재 후 수동 재시도 경로가 검증된다.
- 기본 저장·중복 방지·통화별 맥락 격리가 검증된다.
- 실제 사건과 저장 기록이 일치한다.
- 관련 자동 검사와 코드 리뷰를 통과한다.
- 비밀값·개인 전화번호·개인정보를 제외한 검증 근거가 남는다.
- 변경 내용을 commit하고 기존 승인된 원격 저장소에 push한다.

실통화 완료 근거에는 다음을 남긴다.
- 검증 일시
- 검증한 커밋과 실제 사용 런타임 버전
- A/B의 역할만 표시한 통화 순서
- 익명화된 요청·시도 식별자
- 각 통화의 연결·종료 결과
- 질문·답변에 따른 업무 상태 변경
- 재시도·수정 여부
- 통과한 시나리오와 남은 실패

원음 녹음이나 전체 전문 보존을 임의로 추가하지 않는다.

health 응답, WebSocket 연결, 프로세스 존재, 자동 테스트 통과, API 모의 응답만으로 실통화 완료를 선언하지 않는다.

외부 계정 제한·연결 설정·수신자 부재 때문에 실통화를 완료하지 못하면:
- 정확히 어느 단계가 막혔는지,
- 무엇을 직접 확인했는지,
- 어떤 구현은 끝났는지,
- 마지막으로 무엇이 필요한지
를 구분해서 보고한다.
“전화가 된다” 또는 goal complete라고 쓰지 않는다.

작업 중 질문은 실제로 없는 입력이나 범위를 바꾸는 결정에만 한정한다.
이미 합의한 제품을 다시 설명해 달라고 요구하지 않는다.
진행 보고는 원인·조치·검증 결과 중심으로 짧게 한다.
