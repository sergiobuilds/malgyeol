## 1. 목표와 실행 승인

말결을 해커톤에서 실제로 작동하고 시연할 수 있는 제품으로 구현하라. 계획만 쓰거나 작업 목록만 남기고 끝내지 않는다. 실제 전화와 실제 데이터·백엔드가 연결된 아름다운 프론트, 발표 덱과 정책 제안서까지 완성한다.

필수 산출물은 다음과 같다.

| 산출물 | 완료의 의미 |
|---|---|
| Manyfast 연결 | 인증된 MCP 초기화·도구 조회·대상 작업공간 접근 성공 |
| Manyfast PRD | 합의·흐름·요구사항·수용기준을 저장하고 도구로 재조회하여 내용 확인, 사용자 접근 링크 확보 |
| 네 사업 데이터망 | 서울 공개 목록과 이용 경로를 출처와 함께 구축, AI와 담당자가 같은 데이터 조회 |
| 전화 | 시민 수신 → 기관 발신·실제 대화 → 답변 반영 → 시민 실제 회신, 분기와 재선택 검증 |
| 프론트 | Claude가 실제 KRDS MCP를 사용해 설계·구현하고 실제 API에 연결, 시각·접근성·업무 흐름 검증 |
| 발표·정책 | 주장과 실제 증거가 연결된 덱·제안서·대본·시연 자료, 편집 원본과 제출 형식 산출물 |
| Future | 합의된 후속 제품·운영 논의를 보존하고 MVP와 구분, 임의 축소 없음 |
| 인계 | 검증 근거, 실행 방법, 변경 커밋, 남은 외부 조건을 정확히 기록 |

이 프롬프트를 사용자가 새 세션에 실행 지시로 전달하면, 여기 명시된 범위의 조사·설계·계획 파일 작성·로컬 구현·검증·문서 작성·Manyfast PRD 생성/갱신·기존 원격 저장소 일반 push를 수행하라는 지시로 취급한다. 사용자에게 같은 범위의 착수 허락을 반복해서 묻지 않는다.

`looprun`의 GATE_0과 GATE_1에 대해서도 이 프롬프트를 실행 지시로 받은 것을 이 범위 안의 사전 승인으로 사용한다. 단, 전략과 3종 문서는 실제로 작성·검토하고 각 전이를 순서대로 기록한다. 작성하지 않은 계획을 승인 완료로 표시하거나 상태 파일만 통과시키지 않는다. 제품 범위 변경, 새 외부 비용·공급자 추가 등 이 계약 밖의 선택은 이 사전 승인에 포함되지 않는다.

실제 통화는 승인된 A/B 역할극 범위에서 수행한다. 최신 사용자 지시는 취침 중 인증이나 수신자 응답을 이유로 일을 미뤄두지 말고 의도를 파악해 전체를 완수하라는 것이다. 기존 정상 로그인·OAuth를 복구하고, 수신자 참여가 없으면 기존 ClawOps·Gemini 안에서 실제 전화망에 연결되는 자동 역할극 수신자를 구성한다. 자동 역할극의 구체 구현은 이 지시를 충족하기 위한 실행 선택이며 과거에 사람이 확정한 설계라고 주장하지 않는다. 아래 14절의 무인 검증 계약을 적용한다. 잠든 사용자의 개인 단말에 반복 발신하지 않는다.

production 배포, 공공기관 직접 접촉, 외부 제출·발송, 원격 저장소 신규 생성, 기존 타 세션·프로세스 종료, 파괴적 변경은 별도 승인 범위를 확인한다. 해당 승인이 없으면 로컬 검증과 배포·제출 가능한 산출물까지 완성한다. 로컬 제품 완성과 production 배포 상태를 따로 보고한다.

## 3. 반드시 looprun --auto로 직렬 실행

여기서 auto는 `looprun`의 `mode=auto`다. Ouroboros auto, Ralph, 병렬 구현 엔진으로 바꾸지 않는다.

`~/.config/agents/shared/skills/looprun/SKILL.md`, `templates.md`, `executor-cheatsheet.md`를 읽는다. 실제 상태 파일 형식과 hook도 확인한다. 기존 다른 작업의 `.looprun-state`를 덮어쓰지 않는다.

`dev/active/malgyeol-product-completion/`에 다음 3종 실행 문서를 만든다.

- `plan.md`: 목적, 아키텍처, 섹션별 목적·장단점·예상 문제·해결책·완료기준·검증·의존성. 구현 코드를 계획에 넣지 않는다.
- `tasks.md`: 각 섹션의 구현·리뷰·executor·셀프체크 체크리스트와 수용기준 연결.
- `context.md`: 근거, 설계 결정, 계획 변경, 실제 도구·버전·연결 상태, 검증 결과, 차단 사유와 다음 행동.

한 번에 활성 구현 섹션은 정확히 하나다. 데이터·전화·프론트·덱을 동시에 구현하지 않는다. 여러 코딩 에이전트, 백그라운드 구현, 병렬 worktree로 속도를 내지 않는다.

각 섹션은 다음 순서로 수행한다.

- 파일에서 plan.md와 현재 상태를 다시 읽는다.
- 해당 섹션 상세 설계와 완료기준을 확인하고 시작을 알린다.
- 구현한다. TODO·placeholder·성공을 꾸미는 임시 분기로 완료시키지 않는다.
- Codex 코드 리뷰를 실제 실행하고 이슈를 수정한다.
- executor로 실제 동작을 검증한다. 타입·빌드 외에 해당 API·저장·통화·브라우저 흐름을 실행한다.
- 셀프체크와 CHRONICLE 기록 필요 여부를 확인한다.
- 근거가 있을 때만 tasks.md를 체크하고 `section_N_done`으로 전이한다.
- auto 모드로 다음 섹션을 시작한다.

필수 문구인 `섹션 N codex 리뷰 완료`, `EXECUTOR 섹션 N PASS`, `섹션 N 셀프체크 완료`, `섹션 N CHRONICLE 확인 완료`는 해당 작업을 실제 완료했을 때만 context.md에 기록한다.

외부 의존 때문에 섹션을 재배치할 때는 먼저 해당 섹션의 코드 작업을 멈춘다. plan.md 변경 이력에 원래 수용기준 ID와 이유를 기록하고, 이미 독립적으로 검증 가능한 구현 부분과 외부 검증 부분을 별도 섹션으로 분해한다. 외부 검증의 모든 수용기준은 tasks.md에 미체크로 그대로 유지하고 최종 완료 의존성에서 제거하지 않는다. 현재 구현 부분이 자체 수용기준·리뷰·executor를 실제 통과한 경우에만 정상 section_done 전이를 한다. 그것도 불가능하면 상태를 유지하며 문서·읽기 조사만 수행하고 hook을 우회하지 않는다. 외부 조건을 확보하면 미완료 검증 섹션을 다음 실행 대상으로 복귀시킨다. 상태 이름을 임의로 만들거나 전체 goal 완료 조건을 낮추지 않는다.

섹션 검증 수정·재검증 최대 5회, 최종 리뷰 최대 10회라는 looprun 상한을 지킨다. 횟수를 초기화하거나 작업명을 바꿔 같은 실패를 무한 반복하지 않는다.

최종 리뷰도 사용자 직렬 지시에 따라 순차 실행한다. 스킬의 병렬 리뷰 예시는 이 작업에 적용하지 않는다. 지정·허용된 리뷰 모델만 사용하고, 허용된 두 번째 리뷰 수단이 없으면 임의 모델을 추가하지 말고 실제 검증 범위를 기록한다.

프론트는 Claude에게 한 섹션씩 직렬 위임한다. 그동안 주 에이전트는 다른 구현을 진행하지 않는다. Claude 결과를 통합·리뷰·검증한 뒤에만 다음 섹션으로 간다. Claude에 전달하는 계약에도 재위임 병렬 구현 금지를 명시한다.

## 4. 제품 전체 계약

시민이 생활상의 필요를 말하면 말결이 요청을 맡아 실제 지원사업·기관·이용 경로 데이터를 조회하고, 기관에 필요한 조건을 확인·조율하며 허용된 연결을 이어가고 시민에게 결과를 회신한다.

주 사용자는 다음과 같다.

- 시민: 사업명을 알거나 앱을 조작할 필요 없이 전화로 이용한다. 기관에 직접 찾아가거나 문의하기 어려운 상황을 중심에 둔다. 특정 연령·장애 유형으로 이용을 제한하지 않는다.
- 지원 연결 담당자: 데이터망, 시민 요청, 필요별 진행, 기관 답변, 남은 일과 개입 동작을 대시보드에서 다룬다.
- 기관: 기존 업무 창구로 문의를 받는다. 새 기관 포털이나 회원가입을 필수로 요구하지 않는다.

네 사업은 푸드뱅크·푸드마켓, 찾아가는 푸드마켓, 그냥드림, 돌봄SOS로 고정한다. 다섯 번째 사업·범용 복지 검색·결제·정산·배송 운영을 임의 추가하지 않는다.

대표 사례는 “쌀은 있는데 밥하기 어렵고 비누도 필요하며 가지러 갈 수 없다”다. 조리 어려움·식사·생필품·방문 제약을 구별한다. 쌀 키워드를 쌀 주문으로 바꾸지 않는다. 대표 사례가 전체 제품의 범위가 아니며 네 사업을 한 사람에게 억지로 모두 연결하지 않는다.

한 요청에 여러 필요가 존재한다. 식사가 연결됐으면 유지하고 생필품만 재탐색할 수 있다. 거절·조건 변경·취소가 전체 요청을 덮어쓰지 않는다.

기관의 자격 판단·제공 판단은 기관에 둔다. 시민에게 허용받은 범위에서 신청 의사 전달·상담 연결·일정 조율을 수행한다. 실제 행정 시스템 연동을 Future로 미루는 것을 이유로 전화의 대리 수행을 안내만으로 축소하지 않는다.

전면에는 행동 중심 진행과 다음 행동을 보여준다. 미확인·미검증·목업·연습용·placeholder 등 개발 단계 설명 배지를 반복하지 않는다. 실제로 하지 않은 연락·접수·제공은 완료로 표시하지 않는다. 기관 직접 문의를 시민에게 떠넘기는 문장으로 흐름을 끝내지 않는다.

## 5. Manyfast MCP 복구와 PRD 완성

Manyfast MCP를 실제로 연결하고 PRD를 생성한다. 로컬 Markdown만 작성한 것을 Manyfast PRD 완료로 대체하지 않는다.

이전 세션에서 확인한 상태:

- Claude 설정의 Manyfast 주소: `https://api.manyfast.io/mcp`.
- 저장된 OAuth로 MCP 접속 시 `401 token_expired`.
- refresh 요청은 form, JSON 등에서 `400 invalid_request`가 발생했고 복구되지 않았다.
- discovery는 `https://api.manyfast.io/.well-known/oauth-authorization-server`에서 읽었다.
- 당시 metadata는 refresh_token grant와 token endpoint auth method `none`을 광고했다.
- 이 결과만으로 refresh token 폐기·서비스 장애·재로그인 필수를 단정하지 않는다.
- PRD는 아직 생성되지 않았다.

먼저 현재 연결·OAuth metadata·등록 client·refresh 계약을 조사한다. 기존 공식 MCP 클라이언트의 정상 인증 경로를 우선 사용한다. 토큰·client secret·인증 코드·쿠키를 출력하지 않는다. 무작위 파라미터 재시도나 인증 우회를 하지 않는다. 실패한 갱신 요청이 기존 자격증명을 덮어쓰지 않게 한다.

갱신 실패만으로 중단하지 않는다. 공식 클라이언트의 갱신 계약을 확인하고, 기존 로그인 브라우저 세션을 통한 정상 OAuth 재연결까지 수행한다. 이 PRD 작업에 필요한 기존 계정의 정상 연결 동의는 사용자 지시 범위에서 처리한다. 다른 계정이나 더 넓은 권한을 선택하지 않는다. 비밀번호·OTP·CAPTCHA처럼 사용자 본인만 할 수 있는 절차가 실제로 나타나면 이를 우회하거나 답을 만들어내지 않는다. 그 전까지 연결 불가라고 추정하지 않는다.

연결 후 실제 도구 schema를 읽고 다음을 수행한다.

- 사용자 작업공간과 기존 말결 프로젝트·문서를 조회한다.
- 기존 적합한 PRD가 있으면 최신 내용을 먼저 읽어 중복 생성을 피한다.
- 해당 말결 작업공간에 아래 요구사항을 담은 PRD를 생성·갱신한다.
- 도구가 구조화된 요구사항·흐름·문서 기능을 지원하면 그 기능에 맞게 구성한다. 지원하지 않는 기능을 사용했다고 주장하지 않는다.
- 저장 후 별도 조회로 제목·본문·요구사항·흐름이 실제 저장됐는지 확인한다.
- 문서 ID, 사용자 접근 링크, 검증 시각을 context.md에 기록한다.
- 사용자 지정 권한을 넘는 공개 공유·초대는 하지 않는다.

PRD에는 최소한 다음이 포함돼야 한다.

| 영역 | 구체화할 내용 |
|---|---|
| 문제·목표 | 시민의 기관 간 확인·조정 부담, 실제 지원 연결, 담당자 업무 |
| 사용자 | 시민·담당자·기관의 역할과 이용 경로 |
| 범위 | 네 사업, 서울 공개 목록, MVP와 Future, 임의 추가 금지 |
| 시민 흐름 | 접수, 필요·제약, 음성 동의, 기관 연락, 조건 선택, 회신, 후속 |
| 담당자 흐름 | 지원망 탐색, 요청 목록, 요청 상세, 문의·답변 확인, 개입, 후속 |
| 데이터 | 사업·기관·사업장·관할·이용 경로·근거·요청·필요·문의·답변 |
| 업무 상태 | 연락 전/중/후, 부재·거절·조건 변경, 부분 해결, 시민 선택, 제공 구분 |
| 동작 | 조회·필터·상세 진입·정정·중단·재시도·결과 확인 |
| 프론트 | Claude 소유, 엄격한 KRDS MCP 사용, 업무 흐름·접근성·반응형 요구 |
| 예외 | 빈 목록, 조회 실패, 통화 실패, 결과 불명, 중복, 오래된 답변, 수정 충돌 |
| 검증 | 요구사항별 입력·행동·예상 결과·증거, 실통화와 모의 검증 구분 |
| 제출물 | 덱·정책 제안서의 주장과 기능·시연 증거 연결 |

화면 명세는 단순 페이지 이름 목록으로 끝내지 않는다. 각 화면의 목적, 진입점, 읽는 정보, 가능한 행동, 행동 전제, 성공 후 변화, 실패·빈 상태, 다음 이동, 연결 API와 수용기준을 적는다. 세밀한 화면 분할과 와이어프레임은 Claude가 이 PRD에 맞춰 결정한다.

Manyfast에 개인정보·전화번호·인증정보를 넣지 않는다. 예시는 설명용임을 내부 명세에서 구별하고 실제 공공기관 참여 실적으로 만들지 않는다.

인증 진단과 정상 재연결을 끝까지 수행하며 PRD의 요구사항 내용·추적표·저장 입력도 준비한다. 로컬 초안을 최종 산출물로 대체하지 않는다. Manyfast에 저장하고 재조회하는 것까지 작업으로 유지한다. 사용자 전용 인증이 실제로 차단할 경우에만 그 정확한 경계와 재개 가능한 입력을 남긴다. 같은 내용을 여러 문서의 독립 정본으로 늘리지 않는다.

## 6. 네 사업 데이터망 구현

인계문 4.1절의 공식 출발 URL을 직접 읽어 현재 자료를 수집한다. 기억이나 예전 자료만으로 현재 사업 조건을 확정하지 않는다.

서울 전체 공개 목록 수집과 기관별 상세 경로 구축을 구별한다. 페이지·지역·건수·중복·누락·수집시각을 기록한다. 전체 서울 목록을 대표 자치구만으로 바꾸지 않는다. 공개 자료가 없는 항목은 근거 없는 값으로 채우지 않는다.

사업, 운영기관, 사업장, 사업별 운영, 관할, 이용 경로, 목적별 창구, 필드별 근거를 분리한다. 전화와 FAX를 구별한다. 주소의 지역을 관할로 자동 대체하지 않는다. 같은 시설의 여러 사업·시간·절차를 유지한다.

네 사업의 절차 차이:

- 푸드뱅크·푸드마켓: 이용 대상·등록·선정·물품 수령. 개인 제공처와 물류·기부 창구 구분.
- 찾아가는 푸드마켓: 운영기관·지역·장소·일정·방문 제공 방식. 개별 가정 배달을 자동 가정하지 않음.
- 그냥드림: 사업장·해당 사업 시간·준비물·방문 차수별 절차. 같은 시설 타 사업과 분리.
- 돌봄SOS: 거주지 신청 창구·서비스별 상담/판단·제공기관 관계. 상품 주문으로 만들지 않음.

검색·필터·후보 선택은 관할·조건·접근 가능성·시점·시민 선호를 반영한다. 거리만으로 결정하지 않는다. 선택·제외 이유와 추가 확인할 조건을 보존한다.

공개 정보와 특정 시민에 대한 기관 답변을 분리한다. 개인별 답변을 일반 지원 조건으로 자동 승격하거나 공개 캐시에 노출하지 않는다. 최신 답변이라는 이유만으로 기존 근거를 덮어쓰지 않는다.

실시간 재고 API·전 기관 협약을 시작 조건으로 요구하지 않는다. 공개 데이터와 실제 문의를 연결한다. 수집 오류·누락과 완전성은 사실대로 기록한다.

## 7. 전화 구현과 실통화 계약

`phone-goal-prompt.md` 전체를 실행 계약으로 적용한다. 다음 7개 확정 사항을 다시 질문하지 않는다.

- ClawOps + Gemini 유지. 시민 접수·기관 통화·시민 회신을 역할별로 분리하고 같은 요청에 연결.
- 생활 언어에서 여러 필요와 제약 이해. 키워드만으로 품목 확정 금지.
- 업무 단위 음성 동의. 숫자키는 보조.
- 시민 통화 후 기관 실제 발신. 조건 확인·방법 조율·허용된 신청 의사 전달·일정 조율.
- 해결된 필요 보존, 거절된 부분만 대안. 비용·일정·방문 방식의 중요한 변경은 시민 재선택.
- 시민에게 실제 회신. 선택에 따라 기관에 다시 연락. 안내만 하고 종료 금지.
- MVP 전체 런타임에서 한 번에 한 통화. 부재 저장·담당자 수동 재시도. 자동 재연락 예약·3자 통화는 Future.

한 번에 한 통화 정책에는 시민의 예기치 않은 추가 수신도 포함한다. SDK의 수신 허용·통화 제어 기능을 조사해 현재 진행 중인 통화를 침범하지 않는 처리를 구현하고, 접수하지 않았는데 접수됐다고 안내하지 않는다.

현재 코드의 키워드 선택·고정 시민·숫자키 강제·연습용 대사·정상 변경 차단을 합의된 구조로 교체한다. SDK에 발신 함수가 있는 것과 계정·오디오·요청 처리의 전체 성공을 구별한다.

통화 역할·요청 맥락이 첫 인사 전에 설정되는지 확인한다. 기관에 시민 접수 인사를 하거나, 회신에서 같은 사정을 처음부터 다시 묻거나, 다른 시민의 정보가 섞이면 실패다.

요청 ID·필요 ID·기관 ID·문의 ID·통화 ID를 구별한다. 통화 종료는 요청 완료가 아니다. 기관 수락·접수·일정 확정·실제 제공을 구별한다. 결과 불명 발신을 무조건 재시도하지 않는다.

시민 회신은 등록 번호 일치만으로 민감한 요청 내용을 공개하지 않는다. 역할극에서 사전에 정한 확인 방식으로 요청 당사자/역할을 확인한 뒤 상세 결과를 말한다. 다른 사람이 받거나 음성사서함·확인 실패인 경우 일반적인 연락 목적만 남기고 상세 개인정보·필요·기관 답변 공개는 보류한다. 정식 본인 인증 전체는 Future로 두되 이 최소 보호와 다른 수신자·자동응답기 분기는 자동 역할극에서도 검증한다.

기관 질문에는 실제 시민의 제약을 반영한다. 방문할 수 없는 시민에게 방문 수령 가능 답변을 얻었다고 해결로 처리하지 않는다. 애매한 답변은 같은 통화에서 조건을 구체화한다. 허용 범위 밖 개인정보나 새로운 업무를 전달하지 않는다.

A/B 역할극은 실제 음성으로 수행한다. 기관 역할 수신 번호 매핑은 실제 기관 데이터와 분리한다. 실제 공공기관에 무단 발신하지 않는다. 사람이 통화할 시간이 없으면 14절의 통제된 자동 역할극 수신자로 실제 전화망의 수신·발신·회신·재선택까지 검증한다. 모델 내부 대화나 API mock으로 전화망 검증을 대체하지 않는다.

## 8. 반드시 실제 KRDS MCP를 사용한 Claude 프론트

프론트 설계·와이어프레임·디자인·구현·시각 완성도는 기존 합의대로 Claude가 맡는다. Codex가 대신 임의 UI를 만들지 않는다. 사용자 요청은 프론트까지 완성하라는 것이므로 Claude 작업을 실제로 실행·통합·검증해야 한다. 인계만 하고 종료하지 않는다.

KRDS 기준은 `https://github.com/KRDS-uiux/krds-uiux`이며 **KRDS MCP 실제 사용이 필수**다. README만 읽거나 비슷한 CSS를 만든 것을 MCP 사용으로 보고하지 않는다.

현재 확인된 연결 단서:

- Claude 사용자 설정에 서버 이름 `krds-mcp`가 등록되어 있다.
- 실행 설정은 `npx -y @krds-mcp/krds-mcp`다.
- 등록 상태만 이번 세션에서 읽었다. 실제 새 세션의 초기화·도구 호출은 다시 검증해야 한다.

프론트 착수 전에 다음을 완료한다.

- Claude 실행 환경에서 실제 KRDS MCP 서버를 초기화하고 도구 목록/schema를 읽는다.
- 제공하는 디자인 원칙·토큰·컴포넌트·패턴·접근성 지침을 실제 호출로 조회한다.
- 필요한 버튼·입력·선택·검색·표·목록·상태·탐색·알림·대화상자 등의 구성요소에 해당하는 근거를 확보한다. 도구가 제공하지 않는 항목은 공식 KRDS 자료에서 보완하되 MCP 호출을 대체하지 않는다.
- 사용한 도구명·호출 목적·참조 문서/컴포넌트·버전 또는 확인시각을 기록한다.
- 프로젝트의 KRDS design-forge pack과 기존 디자인 파이프라인을 조사하고 그대로 연결한다. 관련 스킬을 읽는다. 기존 생성물이 있으면 최신 여부와 일치성을 확인한다.
- MCP와 파이프라인에 오류가 있으면 원인을 고친다. 다른 디자인시스템으로 바꾸거나 MCP 없이 완성했다고 주장하지 않는다.

Claude에 전달할 계약:

- 최신 Manyfast PRD 또는 인증 대기 중 준비된 동일 요구사항, 데이터/API/이벤트 계약, 전화 확정 동작, KRDS MCP 사용 의무.
- 프론트는 담당자의 실제 지원 연결 업무를 중심으로 구성한다.
- 섹션 하나씩 구현하며 다른 구현 worker를 동시에 띄우지 않는다.
- 화면·컴포넌트 선택은 KRDS 근거에 연결한다. 임의 팔레트·타이포·버튼·폼으로 KRDS의 핵심 규칙을 덮지 않는다.
- 공식 패턴만으로 부족한 업무 표현은 기존 KRDS 토큰·구성요소를 조합하고 확장 근거를 기록한다.
- 아름다움은 조밀한 장식이 아니라 정보 위계·간격·타이포·정렬·상태 표현·일관된 상호작용에서 확보한다.
- 빈 카드·작동하지 않는 버튼·하드코딩 통계·시간에 따라 자동 성공으로 바뀌는 진행 표시 금지.
- 데이터가 없거나 실패한 경우도 제품의 다음 행동을 제공한다.

필수 업무 흐름:

| 흐름 | 보여줄 정보와 실제 행동 |
|---|---|
| 지원망 탐색 | 네 사업·지역·관할·기관·이용 조건 검색/필터, 사업별 이용 경로 상세 |
| 요청 목록 | 시민 요청 요약, 필요별 진행, 최근 행동, 개입 필요 여부, 상세 진입 |
| 요청 상세 | 시민의 필요·제약·동의 범위, 복수 필요별 진행, 후보 선택 이유 |

특정 페이지 수나 레이아웃을 주 에이전트가 미리 강제하지 않는다. Claude가 흐름과 KRDS 근거를 바탕으로 세밀한 화면 명세·와이어프레임을 만들고 구현한다.

데스크톱과 모바일/좁은 화면, 키보드 탐색, 포커스, 레이블, 오류 안내, 명도 대비, 긴 한글 텍스트, 표·목록의 넘침을 검증한다. 자동 접근성 검사만으로 시각 QA를 대체하지 않는다.

## 9. 공통 API·이벤트·저장과 실제 통합

프론트와 전화가 같은 도메인·저장을 사용하게 한다. 화면용 가짜 데이터 저장소와 AI용 실제 데이터를 따로 운영하지 않는다.

계약에는 사업·기관·요청·필요·문의·시도·답변·회신 식별자, 상태, 근거, revision, 입력 검증, 오류 형식, 역할별 접근, 멱등성을 명시한다. 함수명·파일명은 현재 코드에 맞춰 정한다.

필요한 동작은 데이터 조회, 요청 생성/조회/정정, 문의 준비/실행, 동의·시민 선택 기록, 답변 저장, 회신, 중단, 수동 재시도다. 모델은 이해·질문·설명을 하고 코드는 권한·연락처·중복·상태 전이를 통제한다.

백엔드 사건으로 화면이 갱신되어야 한다. 현재 스택에 적합한 갱신 방식을 선택해 중복·연결 끊김·재연결을 처리한다. 공급자 이벤트를 받기 전에 화면에서 연락 성공을 예측 표시하지 않는다.

기관 답변 후 요청 상세를 새로 열어도 같은 결과를 보여야 한다. 담당자 정정 후 대기 연락·시민 회신에 변경이 반영돼야 한다. 요청 A의 사건이 요청 B에 나타나면 실패다.

기존 SQLite와 역할 토큰·내부 agent 인증을 조사해 재사용한다. 데이터 마이그레이션·백업·복원, 비밀값 로깅 방지, 개인 연락처 분리, 불필요한 원음 저장 금지를 적용한다. 상용 인증 전체를 구현하느라 MVP를 막지 않되 타인 요청 접근을 허용하는 구조로 만들지 않는다.

## 10. 발표 덱·정책 제안서·시연 자료

이 산출물은 최우선이다. 초반에 전달할 주장·장면·필요 증거를 정하고 구현이 끝난 뒤 실제 증거로 채운다. 기능을 다 만든 후 남은 시간에 급히 붙이지 않는다.

공식 공고·심사 기준·마감·제출 형식·발표 시간을 직접 확인한다. 저장소의 이전 제출 자료는 구 방향일 수 있으므로 그대로 내보내지 않는다. 이전 문서의 3분·1장·20~30명·4~8주를 공식 규격이나 사용자 확정값으로 간주하지 않는다.

덱은 다음을 한 이야기로 연결한다.

- 시민이 기관을 찾고 같은 사정을 반복 설명하고 조건을 조율해야 하는 문제.
- 네 사업의 실제 기관·이용 경로 데이터 기반.
- 시민 요청을 맡아 기관에 실제 문의하고 답변에 따라 이어가는 말결의 행동.
- 전화 결과가 담당자 화면에 반영되고 필요한 개입이 다시 전화에 반영되는 장면.
- 정상·부분 해결·조건 변경 시연에서 확인한 증거.
- 서울시에 필요한 데이터·창구·연계·실증 요청.

정책 제안에는 다음을 포함한다.

- 네 사업의 기관·목적별 창구·이용절차 데이터와 갱신 체계.
- 운영 일정·제공 가능 정보의 공유.
- AI 확인전화를 받을 기관 창구.
- 동의 기반 문의·신청 보조의 허용 범위.
- 해결이 막힌 요청의 실제 사람 인계 체계.
- 제한된 지역·기관의 실증 제안과 측정 항목.

정책 수신 부서와 현재 제도 사실은 공식 근거로 확인한다. 근거 없이 법 개정이 필수라고 주장하지 않는다. 수요·구매의사·기관 협조 조사를 이번 제작의 선행조건으로 추가하지 않는다. 경제성·효능 수치를 만들어내지 않는다.

편집 가능한 원본, 실제 제출 형식, 발표 대본, 시연 순서, 장애 시 전환 자료, 심사 Q&A를 준비한다. PDF는 실제 렌더해 잘림·폰트·페이지·링크를 확인한다. 영상은 실제 확보한 화면과 통화 증거로 구성하고 개인정보를 제거한다. 실통화가 없으면 해당 영상·증거를 완료로 표시하지 않는다.

녹음 보존에 대한 기존 계약을 확인한다. 검증을 이유로 원음·전문 녹음을 임의 추가하지 않는다. 녹음 승인이 없으면 비식별 사건 기록과 허용된 화면 자료로 준비하고 필요한 추가 승인을 분리한다.

준비된 수신자와의 통화를 실제 공공기관 참여·협약·지원 제공 실적으로 주장하지 않는다. 외부 제출이나 발송은 별도 승인 없이 하지 않는다.

## 11. Future 보존과 합의 추적

## 13. 검증 행렬과 통과 증거

자동 테스트는 관할·후보 선택·요청 격리·동의·상태 전이·부분 해결·중복·저장·변경 경합에 집중한다. 기존 171개 테스트 기록은 현재 제품 완료의 증거가 아니다. 현재 명령을 실제 실행한다.

| 계층 | 필수 검증 |
|---|---|
| 도구 | Manyfast 인증·PRD 재조회, KRDS MCP 실제 호출 |
| 데이터 | 네 사업 구별, 관할/주소 차이, 목적별 창구, 출처, 중복·누락 |
| 이해 | 쌀 보유/조리 어려움 구별, 복수 필요, 부정·정정·취소·잡담 |
| 권한 | 업무 동의, 중요 조건 재선택, 허용 번호, 다른 요청 접근 차단 |
| 실행 | 한 통화, 중복 이벤트, 불명 결과, 수정·중단 후 이전 작업 실행 차단 |
| 저장 | 통화와 요청 구별, 재시작 복원, 기존 데이터 보존 |
| 전화 | 실제 수신·기관 발신·양방향 음성·시민 회신·선택 후 재연락 |
| UI | 목록/상세/필터/개입/오류/빈 상태, 실제 사건 반영, 콘솔 오류 |
| KRDS | 실제 조회 근거, 토큰·컴포넌트·패턴 일치, 접근성·반응형·시각 완성도 |
| 제출 | 공식 규격, 근거 없는 주장 없음, 원본/렌더/시연/Q&A |

실통화 필수 시나리오:

- 정상 왕복: A 접수 → B 문의·답변 → A 회신.
- 부분 해결: 식사 등 한 필요는 유지하고 다른 필요만 대안 처리.
- 중요 조건 변경: B의 조건 변경 → A 선택 → 필요한 B 재연락.
- 부재: 수신자와 협의한 미응답 → 실패 저장 → 담당자 수동 재시도.

첫 인사, 왕복 청취, 답변 반영, 말 끊기·침묵·재질문, 세션 종료와 다음 통화 격리를 확인한다. 반복 횟수와 허용 지연은 검증 전에 근거와 수신 가능 시간을 반영해 정한다. 단발 성공으로 안정성을 주장하지 않는다.

브라우저 검증은 실제 로컬 서버에서 수행한다. 새로고침 후 상태 유지, 필터 후 상세·복귀, 다른 요청 이동, 개입 후 백엔드 반영, 실패 후 재시도, 모바일·키보드 흐름을 확인한다. 제품 흐름에서 발생한 JS 오류는 해결한다. 무관한 외부 오류가 있으면 근거와 영향을 별도로 기록한다.

증거에는 검증 일시·커밋·버전·명령·결과·비식별 요청/시도 ID·시나리오별 상태 변화를 남긴다. 개인정보·전화번호·토큰·원음은 승인 없이 포함하지 않는다. 테스트용 합성 이벤트는 자동 테스트 증거로만 표시한다.

## 14. 사용자 취침 중에도 끝내는 인증·실전화 검증

최신 사용자 정정은 “인증이나 수신자 응답이 없으면 미완료로 남긴다”를 기본 실행 방식으로 삼지 말고, 의도를 파악해 모두 수행하라는 것이다. 사용자 응답을 기다리는 것을 편한 종료 조건으로 사용하지 않는다. 이미 합의한 제품을 다시 인터뷰하지 않는다.

### 14.1 인증 복구

- 기존 Manyfast 공식 MCP 클라이언트·OAuth metadata·등록 client와 정상 갱신 요청을 확인한다.
- 기존 로그인된 브라우저·정상 OAuth 재연결 경로를 확인한다. 기존 계정으로 요청 범위의 연결을 복구한다.
- 서버 초기화와 실제 도구 호출, 대상 작업공간 접근, PRD 저장·재조회를 모두 수행한다.
- 만료 토큰이라는 이유만으로 “내일 로그인해 주세요”를 남기고 끝내지 않는다.
- 인증값을 읽어야 하면 기존 보안 저장소를 사용하고 토큰·쿠키·코드를 출력하거나 문서에 복사하지 않는다.
- 사용자 전용 비밀번호·OTP·CAPTCHA가 실제로 요구되면 인증을 우회하지 않는다. 이것은 의도 추론으로 만들어낼 수 있는 값이 아니다. 그 경계까지 정상 복구를 수행한 증거와 재개 지점을 남기고 다른 작업을 완수한다. 대화 무응답을 인증 승인 성공으로 취급하지 않는다.

### 14.2 사람이 없어도 실제 전화망 왕복을 검증하는 수신 환경

- 기존 ClawOps 계정의 등록 번호·수신 라우팅·발신·Gemini 세션 기능을 조사한다. 실제 이미 연결된 자원만 사용한다.
- 준비된 사람이 있으면 승인된 A/B 역할극을 수행한다. 사람이 없으면 시민·기관 역할을 담당하는 통제된 자동 음성 수신자를 구성한다.
- 제품 구현은 직렬이다. 자동 역할극 프로세스가 통화를 받아야 하는 동시 실행은 테스트 장치의 실행이며 여러 구현 에이전트를 병렬 가동하는 것이 아니다. 제품 본체의 한 번에 한 통화 정책은 유지한다.
- 기존 지정 Gemini를 활용하되 기존에 승인된 인증·모델 경로를 유지한다. 실통화와 모델 실행은 기존 계정의 승인된 사용 범위·가용 잔액·등록 한도 안에서 수행한다. 계정의 소비 한도를 확인하고 검증 횟수·최대 통화시간으로 비용 상한을 적용한다. 기존 한도를 찾지 못했다고 임의 무제한 과금을 허용하지 않는다. 새 공급자·새 유료 번호·새 API 키·새 모델·충전·요금제 증액을 임의 구매하거나 추가하지 않는다.
- 시민 역할은 필요와 제약을 말하고, 말결의 질문에 답하고, 음성 동의·변경 선택을 한다. 기관 역할은 문의 맥락에 맞춰 응답하며 거절·일정 변경·방문 조건 등 시나리오에 따라 답한다.
- 실제 전화망을 통과해 수신·발신·오디오가 전달되게 한다. 서로 텍스트를 주고받는 두 모델, 내부 WebSocket만의 연결, 녹음 재생, 호출 성공값 mock으로 대체하지 않는다.
- 실제 계정에 자동 수신이 가능한 자원이 있는지 먼저 확인한다. 개인 휴대폰 번호만 있고 자동 수신 경로가 없다면 자동으로 가능하다고 가정하지 않는다. 기존 승인 자원의 정상 연결 설정으로 해결할 수 있는지 조사하고, 불가능한 자원을 생성했다고 쓰지 않는다.
- 시험 수신자의 기관 역할 설정은 실제 기관 데이터와 분리한다. 실제 공공기관이나 임의 제3자에게 전화하지 않는다.
- 정답·기대 결과·검증 판정은 제품 에이전트에 전달하지 않는다. 역할별 대사와 조건만 전달하고 독립된 검증기가 실제 사건·저장·통화 결과를 비교한다.
- 고정 정상 대본 하나에 맞춰 제품을 최적화하지 않는다. 정상 연결·부분 거절·조건 변경·시민 재선택·침묵·부재·재시도를 포함하고 실행마다 필요한 입력 변형을 적용한다.
- 부재 검증은 통제된 수신 측에서 미응답을 구성한다. 담당자 재시도 API를 호출해 실제 재발신과 중복 차단을 검증한다.
- 자동 음성 역할극 결과는 “자동 역할극 수신자를 이용한 실제 전화망 검증”으로 기록한다. 사람이 직접 듣고 검증했다고 주장하지 않는다. 사람이 참여해야만 알 수 있는 청취 편의성과 실제 시민 사용성은 별도 후속 확인으로 구별한다.
- 별도 전화 프롬프트의 ‘반드시 실제 사람이 응답해야 실통화 통과’ 조건은 이 최신 무인 완수 지시에 따라 이 절로 대체한다. 실제 전화망·음성 왕복·업무 상태 검증 요구는 낮추지 않는다.

### 14.3 끝까지 진행하는 방식

인증이나 수신 환경 한 가지를 조사하는 동안에도 필수 산출물을 누락하지 않는다. 하나씩 직렬로 진행하되 외부 의존이 확인된 항목은 명시적으로 분리해 다른 독립 작업을 완료한 후 다시 연결한다. 미완료 상태를 숨기려고 `section_N_done`을 쓰지 않는다.

- Manyfast: 정상 인증 복구, 실제 PRD 저장·재조회까지 추적.
- KRDS MCP: 실제 연결·컴포넌트 조회·Claude 구현 근거까지 확보. 등록만으로 성공 금지.
- Claude: 허용된 CLI OAuth 실행과 필요한 도구 연결을 복구. Codex가 몰래 UI를 대신 만들지 않음.
- 전화: 통제된 자동 수신 환경과 실제 전화망 검증까지 수행. 수신자 부재만으로 끝내지 않음.
- 제출물: 공식 자료·편집 원본·렌더·실제 시연 증거까지 준비. 근거 없는 숫자나 장면 생성 금지.
- 리뷰: 실행 실패의 원인을 고치고 실제 리뷰. 수행하지 않은 리뷰 PASS 금지.

실패 원인을 고치며 스킬의 수정 상한·서비스 rate limit을 지킨다. 취침 중 완수 의지는 권한 없는 인증 우회, 공공기관 발신, 기존 승인 범위 밖의 구매·충전·증액, 증거 조작의 허가가 아니다. 끝내 해결할 수 없는 외부 경계가 실측되면 전체 완료를 거짓 선언하지 말고 경계와 수행한 작업을 정확히 남긴다.

## 15. 완료 판정·저장·최종 보고

최종 완료는 문서 작성, 빌드 성공, 화면 렌더, WebSocket 연결 중 하나로 판단하지 않는다. 1절 산출물과 13절 검증의 완료 행렬을 만든다.

Manyfast PRD 저장·재조회, KRDS MCP 기반 Claude 프론트, 실제 전화 전체 왕복 중 하나라도 빠지면 전체 goal 완료가 아니다. 외부 조건 때문에 끝낼 수 없는 부분은 정확히 미완료로 남긴다. 기능을 축소하거나 테스트를 삭제해 완료 조건을 맞추지 않는다.

각 섹션의 관련 검사 통과 후 변경을 검토하고 commit/push한다. 다른 작업자의 파일을 함께 커밋하지 않는다. secret·PII를 검사한다. 문서·링크·프로젝트 검사를 통과시키며 hook을 끄지 않는다.

MASTER-MAP·CHRONICLE·PASSDOWN은 현재 사용자 합의와 실제 증거에 맞게 갱신한다. observe-only 권위를 유지한다. 거절된 계획 포인터와 최신 합의 충돌은 정리하되 과거 결정을 지우거나 실행하지 않은 일을 완료로 바꾸지 않는다.

context.md에는 재개에 필요한 최소 상태를 남긴다. 시작한 임시 서버·worker의 소유권과 상태를 기록한다. 다른 세션의 프로세스는 종료하지 않는다. goal 도구가 있는 환경에서는 실제 필수 작업이 남아 있는 동안 goal을 complete로 표시하지 않는다.

최종 보고에는 다음을 제공한다.

- Manyfast PRD 링크와 재조회 결과.
- 실제 KRDS MCP 사용 근거와 Claude 프론트 결과.
- 데이터 수집 범위와 조회·출처 검증 결과.
- 실제 전화 시나리오별 통과/실패와 증거.
- 화면·백엔드·전화 통합 검증 결과.
- 발표 덱·정책 제안서·대본·시연 자료의 GitHub/산출물 링크.
- commit/push 상태와 최종 커밋.
- 남은 외부 조건, 필요한 사용자 행동, 정확한 재개 지점.

사용자가 아침에 읽고 바로 결과를 확인하거나 필요한 마지막 행동만 할 수 있게 보고한다. 보고용 요약과 실제 미완료 상태가 어긋나지 않게 한다.
