발표 덱·정책 제안서의 설득력, 반복 작동하는 실제 전화, 아름답고 기능이 연결된 프론트를 완성하기 위한 실행 계획.

## 1 목표와 계약

말결은 시민이 전화로 생활상의 어려움을 말하면 서울의 네 사업에서 지원 경로를 찾고, AI가 기관에 실제로 전화해 조건을 알아본 뒤 시민에게 다음 행동을 알려주는 제품이다. 시민의 나이·장애 유형을 고정하지 않는다.

| 우선순위 | 목표 | 완료 판정 |
|---|---|---|
| 최우선 산출물 | 발표 덱·정책 제안서 | 문제·제품·작동 증거·서울시에 요청할 일이 한 논리로 연결되고 실제 제출 형식에 맞음 |
| 핵심 증거 | 전화가 매우 확실하게 실제 작동 | 시민 수신·기관 발신·양방향 대화·답변 반영·시민 회신을 같은 빌드에서 반복 통과 |
| 제품 | 화면·데이터·전화가 실제 연결 | 버튼과 상태가 실제 API/사건에 연결되고 준비된 성공 문장만 재생하지 않음 |
| 표현 품질 | 매우 아름답고 빈틈·슬롭 없는 프론트 | 주요 화면·모든 상태·반응형·접근성·문구·시각 QA 통과, Sergio의 화면 확인 |

기능 수는 줄여도 위 네 기준은 줄이지 않는다. 덱·제안서는 마지막 문서 작업이 아니라 초반 설계의 기준이다. 그 주장을 증명할 제품과 화면을 만든다. 녹화본은 현장 장애 대응물이며 실제 작동 합격을 대체하지 않는다.

현재 요청은 계획 작성이다. 코드 구현·실제 전화·배포는 실행하지 않는다. 구현 요청을 받으면 이 계획을 작업 단위로 실행하며 Sergio는 자신/팀원의 두 전화번호로 시민·기관 역할극을 수행하는 시연 방식을 명시 승인했다. 공공기관 연결은 요구하지 않는다. 실제 번호와 연결 유형을 등록해 그 범위 안에서 실행한다. 기존 서비스 종료·새 공급자·API 키 사용·production 배포는 이 문서로 자동 승인되지 않는다.

전체 기능과 운영 계약은 [Future Plan](implementation-plan.md)에 보존한다. 범위를 줄인 이번 MVP가 후속 제품 설계를 삭제하거나 운영 완료를 뜻하지 않는다.

## 2 범위

### 2.1 가져갈 기능

| 영역 | MVP 산출물 | 줄이면 안 되는 경계 |
|---|---|---|
| 네 사업 지원망 | 푸드뱅크·푸드마켓, 찾아가는 푸드마켓, 그냥드림, 돌봄SOS의 실제 기관·역할·연락처·이용절차 | 네 사업 모두 조회·안내·기관 질문·답변·회신 경로 연결 |
| 서울 공개 데이터 | 공식 목록의 페이지/지역을 수집하고 사업 안내 결합 | 대표 지역으로 목록 범위 축소 금지; 주소록만으로 완료 금지 |
| 현실적 구성 데이터 | 실제 기관·사업 절차에 맞는 현재 제공 조건과 준비된 수신자의 답변 | 가상의 기관·실재하지 않는 사업 규칙·허위 공공기관 참여 주장 금지 |
| 시민 전화 | 필요·거주 지역·방문/조리 제약 파악, 필요한 질문, 문의 동의 | 사업명을 먼저 고르거나 긴 자격 설문 강요 금지 |
| 공통 조회 | AI와 화면이 같은 정규화 데이터/API 조회 | 화면 전용 가짜 성공·별도 기관 사실 사본 금지 |
| 기관 전화 | 적합한 창구와 질문 선택, 실제 발신·대화·답변 처리 | 질문 생성·tel 링크·녹음 재생으로 대체 금지 |
| 결과 회신 | 실제 시민 회신 통화, 알아본 결과와 다음 행동 설명 | 기관 답변과 무관한 고정 결과 금지 |
| 부분 해결 | 필요별 상태, 한 필요 유지·다른 필요 대안 연결 | 쌀/비누·두 기관·고정 시민 하드코딩 금지 |
| 담당자 화면 | 지원망 조회, 요청 상세·진행·답변·다음 행동, 정정·재시도·중단 | 장식 지도·통계로 대체 금지 |
| 기본 저장 | 현재 요청·동의·문의·답변·회신 사건 저장 | 통화 종료로 요청 소실, 타인 정보 혼합, 중복 발신 금지 |

서울 전체는 수집 대상이다. 공식 공개 범위의 전체 페이지·지역·건수·중복·누락을 수집 보고로 남긴다. 공개되지 않은 상세 정보를 만들어 전체 구축 완료라고 하지 않는다. 대표 지역의 상세 경로는 더 깊게 구축하지만 나머지 사업을 이름뿐인 메뉴로 만들지 않는다. 출발 URL은 Future Plan 4절을 사용하고 구현 때 원문을 다시 확인한다.

### 2.2 가볍게 구현할 부분

- 시민 정보는 현재 요청 단위로 저장한다. 실제 다중 시민 인증·장기 프로필·새 통화 자동 본인 확인은 Future다. 시연 참여자의 동의받은 연락처는 실행 구성으로 등록한다.
- 문의 목적·전달 내용을 짧게 설명하고 한 번 확인한다. 범용 위임 엔진은 만들지 않되 동의 없는 발신을 막는다. 음성 확인을 우선 설계하고 실제 인식 시험으로 채택, 숫자키는 보조다.
- 같은 필요의 기관 후보는 순차 처리한다. 단일 프로세스 안의 현재 요청 저장·발신 잠금·멱등 처리로 시작하고 분산 큐를 도입하지 않는다.
- 부재·실패는 다음 행동과 재시도 버튼으로 처리한다. 자동 시간표·휴일 계산·여러 차례 재연락은 만들지 않는다.
- 결과 준비 후 시민 회신을 한 번 실행한다. 회신 실패는 저장하고 담당자가 재시도한다. 준비된 결과가 있으면 버튼 한 번으로 실행 가능하되, 정상 흐름은 결과 준비에서 회신까지 연결한다.
- 담당자는 확인·정정·중단·재시도만 수행한다. 부분/전체 인수 배정, 미인수 알림, 자동화 복귀는 Future다.
- 데이터는 수집 스크립트+저장된 버전으로 시작한다. 주기적 자동 갱신·복잡한 충돌 조정·전 기관 재고 API는 제외한다.
- 진행 중 단순 정정·문의 중단은 지원한다. 장기 요청 재개·기관 신청 취소는 Future다.

### 2.3 후속으로 넘길 것

본인 인증·대리권·계정 복구, 여러 날 장기 기억, 자동 재연락/예약, 담당자 배정·책임·상급자 알림, 기관 시스템에 신청·예약·취소 실행, 정교한 개인정보/녹음 관리 화면, 분산 자동 복구·고동시성, 시민 앱·기관 포털·문자·3자 통화·다국어, 배송·제공·정산·결제 추적은 Future로 넘긴다.

수요·구매의사·기관 협조 조사·경제성 분석·상용 운영 설계는 이번 범위에서 제외한다. 다섯 번째 사업과 새 모델/플랫폼을 임의 추가하지 않는다. 기존 기관의 행정 판단을 AI가 대신하지 않는다.

## 3 제품 흐름

### 3.1 두 전화번호 역할극과 정상 흐름

| 역할 | 사용 방법 |
|---|---|
| 번호 A: 시민 | Sergio 또는 팀원이 어르신 역할로 말결에 실제 전화, 질문에 답하고 동의, 이후 결과 회신 수신 |
| 번호 B: 기관 | Sergio 또는 팀원이 푸드뱅크 등 기관 담당자로 AI 발신을 받아 실제 조건·일정·수령 방법을 답함 |
| 말결 서비스 | A 수신 → B 발신·양방향 대화·답변 처리 → A 회신 |

두 번호 역할극은 사용자 승인된 MVP 시연 방식이다. 공공기관 직원과의 실제 왕복을 확인하기 어려워도 이 방식으로 개발·검증한다. 번호 A/B가 개인 단말·가상 번호·서비스 번호 중 무엇인지와 말결 수신 번호와의 관계는 실행 설정에서 확인하며 추측하지 않는다. 가상 번호도 역할 수행에 필요한 양방향 음성을 지원하면 사용한다. 번호 B는 기관별 순차 시도에서 다른 기관 역할을 맡을 수 있으며 서버는 매번 기관 ID·사업·attempt를 구분한다. 공개 기관 연락처를 시험 번호로 덮어쓰지 않는다.

시민/AI/기관 역할 사이 음성·질문·답변 해석·상태·회신은 실제로 수행한다. 전면에 목업 배지를 붙이지 않으며 실제 공공기관 협약·회신 실적을 주장하지 않는다. 협조 확보·기관 조사·공공기관 직접 발신은 이 시연의 선행조건이 아니다.


시민 전화 → 생활 필요·지역·제약 파악 → 네 사업 데이터 조회 → 알려진 절차 안내와 기관 질문 준비 → 동의 → 시민 통화 종료 → 등록된 기관 역할 수신자에게 실제 발신 → 답변 구조화 → 요청·화면 갱신 → 시민에게 실제 회신 → 신청처·준비물·일정·수령 방법과 다음 행동 설명.

바로 답할 수 있는 내용은 첫 통화에서 말한다. 모든 요청을 무조건 발신으로 보내지 않는다. 전화가 필요한 이유를 “이 사람이 지금 어떻게 받을 수 있는가”에 대한 구체적인 조건 질문으로 드러낸다.

### 3.2 부분 해결과 대안

식사·생필품 요청에서 식사 경로는 유지하고, 생필품의 방문 외 수령이 어려우면 그 필요만 다음 적합한 후보로 넘긴다. 기관은 사전에 정한 성공 대사와 다른 표현으로 답할 수 있어야 한다. 후보의 조건이 시민 선호와 다르면 설명·선택으로 돌아간다. 공개 조건과 답변은 실제 사업의 절차를 따라야 한다.

### 3.3 연락 실패

기관 부재·중도 종료 → 시도 기록과 현재 요청 보존 → 대시보드에 다시 연락하기/다른 경로 알아보기 → 담당자의 한 번 재시도로 새 attempt → 성공 시 원래 요청에 답변과 시민 회신 연결. 전송 여부가 불분명한 시도를 무조건 다시 실행하지 않는다.

대표 발표는 식사·생필품 사례로 하지만 제품은 네 사업의 다양한 필요에 데이터 기반으로 동작해야 한다. 위 세 경로가 MVP의 통합 완료 기준이다. Future의 모든 예외를 지금 자동화하지 않는다.

### 4.2 최소 데이터와 API 계약

- 지원망: Program, Organization/Location, ProgramLocation, AccessRoute, FieldEvidence. 기관/사업/연락 창구 ID는 안정적으로 유지한다.
- 요청: Request, Need, Consent, InquiryAttempt, Answer, Callback, Event. 하나의 요청 아래 여러 필요, 기관 시도와 시민 회신을 별도로 둔다.
- 공개 기관 정보와 동의받은 시험 연락처를 분리한다. 수신자 역할 매핑은 서버 실행 설정에서만 처리하고 모델이 공공 연락처를 임의 발신하지 못하게 한다. 화면과 발표에서 실제 공공기관 협약/회신 실적으로 포장하지 않는다.
- API 기능: 지역·필요·사업 조회, 기관/이용경로 상세, 요청 생성/조회/정정, 문의 준비/실행/재시도/중단, 기관 답변 수신, 회신 실행/결과, 진행 이벤트 조회.
- AI와 프론트는 같은 읽기 projection 사용. 개인정보가 있는 요청 API는 기존 인증 기반에서 제한하고 공개 지원망과 분리한다. 시연 시민이 하나여도 데이터 모델은 여러 요청을 구분한다.
- 기관 문의 질문에는 관할·사업·현재 이용 여부·접근 제약에 따라 필요한 것만 넣는다. 연락처는 서버의 기관/역할 ID로 결정한다.
- 상태는 접수·알아보는 중·연락 중·답변 도착·다른 경로 찾기·신청 준비·회신 진행·회신 완료·재시도 필요·중단으로 사용자에게 투영한다. 내부 코드명·원시 오류는 노출하지 않는다.
- 외부 사건 ID와 실행 명령의 멱등키를 저장하고 요청/필요 revision을 비교한다. 늦은 응답·중복 버튼·재접속으로 다른 필요를 덮거나 중복 발신하지 않는다.
- DB 트랜잭션 안에서 모델/전화 네트워크를 기다리지 않는다. 재시작은 요청과 시도를 복원하되 진행 중 통화는 결과 확인 전 자동 재발신하지 않는다.

## 5 전화 합격선

“연결됨” 로그·health 응답·수신 한 번만으로 완료하지 않는다. 발신 기능이 가장 큰 선행 위험이므로 초기에 승인된 수신자와 실제 왕복 경로를 확인한다. 준비된 대화 상대와 실시간 질문·답변·도구 처리·회신을 수행한다. 단순 녹음 재생이나 하드코딩 결과를 사용하지 않는다.

| 게이트 | 확인 항목 | 증거 |
|---|---|---|
| P0 전송 계약 | 설치 SDK/공식 계약에서 발신·양방향 음성·종료·결과 이벤트·시민 회신 지원 확인 | 기능별 지원/제약과 실제 최소 통화 기록 |
| P1 수신 | 시민 말에서 지역·필요·제약을 얻고 필요한 질문·동의 수행 | 요청/동의 사건, 실제 음성 상호작용 |
| P2 기관 | 허용된 수신자에 실제 발신, 적절한 질문, 표현이 다른 답변 해석 | provider call ID·연결/종료 시각·답변·요청 연결 |
| P3 화면 | 기관 답변이 해당 필요와 진행 화면에 반영 | API 사건과 실제 브라우저 결과 일치 |
| P4 회신 | 시민 전화가 울리고 결과·다음 행동을 실제로 설명 | callback ID·연결·종료와 회신 내용 |
| P5 분기 | 거절 후 대안, 부재 후 재시도, 부분 해결 보존 | 각 실제 시도의 결과와 화면 |
| P6 안정성 | 같은 릴리스에서 반복 수행, 한 번 성공만으로 완료 금지 | 아래 반복 결과표와 실패 수정 내역 |

실행 계획의 검증 기준: 공공기관 대신 번호 A/B 역할극으로 최종 빌드에서 전체 정상 왕복을 **연속 3회**, 다른 표현/다른 요청으로 **추가 2회**, 부분 해결·거절 후 대안과 부재 후 수동 재시도를 **각 1회 이상** 통과한다. 이는 제안한 엔지니어링 합격선이다. 사용자 승인된 역할극 범위에서 번호 매핑 후 실행하며 같은 승인을 반복 요청하지 않는다. 시험을 줄여야 한다면 근거와 영향을 보고한다.

음성 잘림·서로 겹치는 대사·피드백 루프·끝없는 침묵·허위 완료 안내·중복 발신·잘못된 요청 연결은 통과 불가다. 발화 종료부터 응답까지, 기관 발신부터 연결까지, 답변부터 화면 반영까지, 회신 완료까지 시간을 기록한다. 고정 지연 성과를 미리 주장하지 않는다. API 사건 도착 후 화면 반영은 목표 2초 이내, 초과하면 화면 갱신 방식을 수정한다.

최종 통화 관련 수정 후 반복 게이트를 다시 통과한다. 발표 직전 승인된 번호로 수신·기관 발신·시민 회신·오디오 장치·브라우저 연결을 점검한다. 녹화본은 이 합격 빌드로 만들고 라이브 기능 대신 사용해 합격 처리하지 않는다.

## 6 Claude 프론트와 연결 계약

프론트 설계·화면 구성·와이어프레임·디자인·구현은 **Claude 전담**이다. Codex는 화면을 설계하거나 수정하지 않고 KRDS pack 설치·디자인 파이프라인 수리·별도 UI 생성도 수행하지 않는다. 이 문서에서 특정 화면 수·배치·라우트·컴포넌트를 확정하지 않는다.

디자인시스템은 반드시 [KRDS-uiux/krds-uiux](https://github.com/KRDS-uiux/krds-uiux)다. 다른 시스템으로 대체하지 않는다. 공식 저장소의 HTML 컴포넌트와 tokens를 2026-09-18 읽기 확인했다. 로컬 `ds list`에서는 KRDS pack이 확인되지 않았고 `ds catalog krds`는 카탈로그 파일 부재를 보고했다. 이는 Claude 착수 참고이며 Codex의 프론트 작업이나 다른 시스템 대체 사유가 아니다.

| 백엔드 연결 계약 | Claude에게 제공할 내용 |
|---|---|
| 지원망 | 네 사업·지역·필요 필터, 실제 기관·사업별 이용 경로·연락 창구·근거 |
| 요청 | 필요·제약·후보 이유·문의 시도·기관 답변·다음 행동·회신 상태 |
| 진행 이벤트 | 요청/필요/기관 ID·revision·시각·통화/답변/회신 결과; 새로고침 후 복원 가능한 조회 |
| 담당자 명령 | 정정·중단·재시도; schema·실패 코드·멱등키·권한 |
| 통합 검증 | 정상·부분 해결/대안·부재/재시도, 긴 기관명/답변, 빈 데이터·서버 오류·재접속 |

전면은 행동 중심으로 표현한다. 화면·AI 대사·덱·제안서에서 미확인·미검증·목업·시연용·합성 데이터·더미·가짜·연습용·샘플·placeholder, 개념 검증 수준·아직 구현되지 않았습니다·실제 서비스가 아닙니다 같은 자기평가·개발 설명 배지를 제거한다. 내부 근거·상태는 유지한다. 실제 행동 없이 연락 완료·지원 승인·제공 완료를 표시하지 않는다. “기관에 직접 문의하세요”만 안내하고 끝내지 않는다. 기술 질의에는 정확히 답한다.

아름다움·빈틈/슬롭 없음·실제 기능 연결이라는 품질 목표는 유지한다. 세밀한 와이어프레임·화면 합격선·시각 검수·Sergio 확인은 Claude가 담당한다. Codex는 API·이벤트 정확성과 데이터 연결을 검증하고 UI 관련 발견은 인계 항목으로 남긴다. 제품 전체 완료에는 Claude의 실제 화면 통합 결과가 필요하다.

## 7 발표 덱·정책 제안서

### 7.1 제작 순서와 공통 논리

초반에 덱의 주장·발표 순서와 제안서 논지를 먼저 쓴다. 제품의 무엇을 보여주면 그 주장이 설득되는지 증거 목록을 붙인다. 개발 중 화면·통화 결과를 채우고 최종 빌드와 동기화한다. 해커톤 공식 공고의 심사 기준·시간·페이지·영상·파일 형식·제출 마감·AI 사용/시연 조건은 M0에서 원문 확인한다. 기존 자료의 3분·1장·20~30명·4~8주를 현행 규정으로 간주하지 않는다.

공통 이야기: 시민이 자기 사정을 여러 기관에 반복 설명하는 부담 → 네 사업의 이용 경로와 현재 조건 사이의 빈칸 → 말결의 실제 기관 확인전화 → 답변에 따라 달라지는 구체적인 다음 행동 → 서울시의 데이터·기관 창구·실증 지원 요청.

### 7.2 발표 덱 구조

아래는 내용 단위이며 슬라이드 수·발표 시간은 공식 형식에 맞춰 조정한다.

| 내용 단위 | 핵심 메시지 | 보여줄 근거 |
|---|---|---|
| 시민 문제 | 앱 사용 여부와 무관하게 필요한 도움을 연결받기 어려움 | 대표 생활 요청과 실제 사업 이용 단계 |
| 말결의 약속 | 한 번 설명하면 필요한 곳에 알아보고 결과를 돌려줌 | 시민 → 기관 → 시민의 실제 전화 흐름 |
| 네 사업 지원망 | 기존 사업을 연결하는 기반 | 실제 기관·역할·절차가 연결된 아름다운 화면 |
| 핵심 시연 | AI가 상황에 맞는 질문을 하고 답을 받아 처리 | 실제 기관 역할 통화와 화면 변화 |
| 답변에 따른 변화 | 거절 뒤에도 다른 필요는 유지하고 대안 탐색 | 부분 해결·다음 후보·회신 장면 |
| 제품의 실제 구조 | 같은 데이터·요청·답변이 음성과 화면을 연결 | 짧은 구조 설명, 기능별 작동 증거 |
| 정책 요청 | 데이터·기관 연락 창구·위임 범위·실증이 필요 | 아래 요청표, 요청과 기능의 직접 연결 |
| 마무리 | 시민의 다음 행동이 구체적으로 정해짐 | 실제 회신 내용과 실행 가능한 제안 |

발표자 대본·장면 전환·라이브 시작/복귀 시점·실패 시 녹화 전환을 함께 준비한다. 기술명 나열·감사/정산 중심의 옛 서사·근거 없는 경쟁 우위·임의 성과 숫자로 채우지 않는다. FAQ는 AI 필요성, 기존 상담과의 관계, 공공기관 역할, 데이터 갱신, 권한, 비용 발생 서비스, 실제 구현 범위에 답한다.

### 7.3 정책 제안서 구조

제안서는 제품 홍보문을 복사하지 않는다. 문제·기존 사업과의 접점·지원 연결 방식·서울시의 결정 사항·실증 설계·기대효과의 측정법을 담는다. 대상자를 고령층으로 제한하거나 모든 사업이 개인별지원계획 기반이라고 쓰지 않는다.

| 요청 | 제품 연결 | 제안서에 명시할 결정 |
|---|---|---|
| 네 사업 기관·창구·절차 데이터 | 정확한 지원망 | 제공 항목·갱신 주체·교환 방식 |
| 운영 일정·제공 가능 정보 | 불필요한 문의/방문 감소 | 공유 가능한 범위와 갱신 책임 |
| AI 문의 수신 창구 | 시민 대신 조건 확인 | 참여기관 역할·문의 범위 |
| 동의 기반 문의·신청 보조 | 안내에서 실제 연결로 확장 | 기관 판단 유지, 허용 업무와 정보 범위 |
| 사람 인계 | 해결이 막혀도 요청 유지 | 담당 주체·인계할 내용·책임 |
| 제한된 실증 환경 | 실제 이용 성과 확인 | 대상·지역·기간·기관·측정 항목을 제안으로 제시 |

정책 담당 부서·법령·사업 조건·공모 규정은 작성 당시 공식 자료로 확인해 출처를 연결한다. 이번에 협약 확보·면담·수요조사를 실행하지 않는다. 경제성·운영·개인정보 계약의 상세는 후속 계획으로 연결한다. 협약·데이터 공유로 해결 가능한 일을 근거 없이 법 개정 요구로 만들지 않는다.

효과는 연결 소요시간·시민 재설명/통화 부담·담당자 개입·경로 안내 결과를 측정하도록 제안한다. 목표·측정법·실측을 구분하고 비용 절감률·일반 효과를 만들어내지 않는다.

### 7.4 납품과 검수

편집 가능한 덱 원본+PDF, 제안서 원본+PDF, 발표 대본/FAQ, 합격 빌드 시연 영상, 제출용 파일 묶음을 만든다. 포맷은 공모 규정으로 최종 확정한다. PDF 폰트·줄바꿈·페이지·잘림·링크·표를 실제 열어 확인하고 발표 시간과 영상 재생을 리허설한다.

문장마다 필요한 근거·제품 장면·시점이 맞는지 대조한다. 완성 화면과 통화 증거는 동일 릴리스에서 가져온다. 실제 공공기관이 참여·승인·제공한 것처럼 쓰지 않는다. 개발 설명 배지는 넣지 않되 기술 질의에 정확히 답할 근거는 준비한다.

최종 심사 관점의 통과 질문: 문제가 바로 이해되는가, 전화가 왜 필요한가, 실제로 작동하는가, 화면이 정교한가, 서울시가 무엇을 결정하면 되는가. 제출 버튼 실행은 별도 대외 작업 승인 범위에서 한다.

## 8 구현 순서와 TDD·병렬 작업

### 8.1 게이트 순서

| 단계 | 수행 | 통과 후 다음 단계 |
|---|---|---|
| M0 주장·규정·전화 위험 확인 | 공고 원문, 덱/제안서 논지, 기존 코드/SDK 발신 계약, 승인된 시험 수신자 준비 | 제출 형식과 전화 왕복의 기술 경로를 확인; 막히면 원인·대안 보고 |
| M1 공통 계약 | 네 사업 데이터 관계, 요청/필요/문의/회신 schema, API·이벤트·역할·시험 수신자 매핑 | 작업자가 서로 다른 API/상태를 만들지 않을 최소 계약 고정 |
| M2 기반 병렬 구현 | 데이터/조회, 요청/통화, 실제 앱 프론트, 덱/제안서 초안 | 실제 데이터·API와 프론트 연결, 최소 왕복 전화 조기 실행 |
| M3 전체 흐름 통합 | 정상·부분 해결/대안·부재/재시도, 실제 회신 | 세 흐름 통합 시험, 실제 화면 상태 일치 |
| M4 완성도와 안정성 | 전화 반복 게이트, Claude의 프론트 시각 QA, 음성/문서 문구·백엔드 상태 정리 | 전화·프론트 합격, 관련 코드 리뷰·회귀 확인 |
| M5 제출물 완성 | 최종 화면/통화 증거 반영, 덱·제안서 PDF, 영상·대본·FAQ, 리허설 | 제출물과 빌드 일치, 시간·형식·렌더 검수 |

전화는 M2 마지막에 처음 시험하지 않는다. M0에서 전송 위험을 먼저 확인하고 M1 직후 최소 왕복을 실행한다. 덱·제안서는 M0부터 시작하고 M2에서 내용이 있어야 한다. 데이터 전체 수집 완료를 기다리느라 전화 위험 발견을 늦추지 않는다.

### 8.2 병렬 구현 시 작업 경계

구현 승인을 받은 뒤 사용할 병렬 분할이다. 현재 문서 작성은 병렬 구현 시작을 뜻하지 않는다. 역할별 파일 소유 범위를 정하고 통합 담당자가 공통 파일을 관리한다.

| 작업 | 독립 책임 | 의존성과 통합 지점 |
|---|---|---|
| 데이터·조회 | 수집/정규화/사업별 절차·지원망 API·조회 테스트 | M1 ID/schema; 프론트/AI가 같은 결과 소비 |
| 요청·전화 | 요청 저장·동의·발신/답변/회신·부분 해결·중복 방지 | M1 API/이벤트; SDK 계약 확인과 실제 통화 승인 |
| 프론트: Claude 전담 | KRDS 필수, 와이어프레임·화면·디자인·구현·시각 QA | Codex는 M1 API/이벤트 계약 제공, UI 파일 수정 금지 |
| 덱·정책 제안 | 공고·근거·논지·슬라이드/문서·FAQ | M0부터 작성, M3/M4의 실제 화면·작동 결과 반영 |
| 통합 | 공통 HTTP 경로·schema 변경·리뷰·세 흐름·릴리스 증거 | 충돌을 한 곳에서 조정, API 변경은 소비자와 함께 검증 |

같은 파일을 여러 작업자가 동시에 바꾸지 않는다. 공통 계약의 변경은 영향받는 작업에 함께 반영한다. 사용 모델·디자인 파이프라인은 기존 지정 범위를 지킨다. 구현 속도는 전화 공급자의 발신/오디오/회신 확인에 달려 있어 실측 전 완료 시간을 약속하지 않는다.

### 8.3 TDD 적용

후보 선택·관할·사업별 경로·추가 질문, 기관 답변에 따른 상태 전이, 부분 해결, 동의 범위, 중복 발신/늦은 답변, 저장·재시작은 실패 테스트 → 구현 → 정리 순서로 한다. 단순 문구·CSS·가역적 스타일 변경에 구현을 그대로 따라 쓰는 테스트를 늘리지 않는다.

모의 adapter로 단위 테스트를 빠르게 실행하되 실제 전화 합격은 실통화로 별도 판정한다. 프론트는 Claude가 실제 API·브라우저·뷰포트·사람의 시각 확인으로 검증한다. 덱·제안서는 실제 PDF/발표 리허설로 확인한다.

## 9 검증과 완료 체크

| 검증 | 필수 조건 |
|---|---|
| 네 사업 | 각 사업의 실제 기관/창구·절차·질문·답변·회신이 연결됨; 대표 외 표현·품목도 처리 |
| 데이터 | 출처·수집 범위·건수·누락, 전화/FAX 분리, 관할·기관 역할·같은 시설 다사업 보존 |
| 요청 | 부분 해결 보존, 잘못된 필요 정정, 중단 이후 발신 방지, 다른 요청 격리 |
| 실행 | 동의 전 발신 0, 허용 수신자 밖 발신 0, 중복 실행 0, 늦은 답변이 최신 조건을 덮지 않음 |
| 복원 | 저장된 요청·문의·답변 재시작 복원, 진행 중 통화 맹목 재실행 금지 |
| 전화 | 5절 반복 실통화 게이트 전체 통과 |
| 프론트: Claude 검증 | 실제 API/통화 결과 연결·시각 품질 결과를 Claude에게 받아 전체 통합 판정 |
| 제출물 | 편집 원본·PDF·영상·대본, 공식 규격·실제 근거·빌드 일치·리허설 |
| 코드 | 변경 코드 독립 리뷰, 관련 신규 테스트와 기존 회귀, `npm run verify`, 저장 전 project-doctor |

기존 데이터 변경 전 SQLite backup API로 snapshot과 복원 검증. 새 흐름은 기존 운영과 분리한 로컬/승인된 시험 경로에서 검증하고 운영 서비스·번호를 임의 교체하지 않는다. 모든 필수 체크 통과 뒤 완료를 보고하며 남은 실패를 녹화나 예쁜 화면으로 가리지 않는다.

## 10 결정할 입력과 위험

아래 항목은 구현 시 확보할 실행 입력이다. 계획 문서 작성이나 덱 논지 작성 자체를 막지 않는다.

| 입력/위험 | 확인 방법·처리 | 닫아야 할 때 |
|---|---|---|
| 공식 마감·발표시간·제출 형식 | 공모 원문/사용자 제공 공고 확인, 기존 3분을 가정하지 않음 | M0, 제출물 분량 확정 전 |
| 번호 A/B의 실제 값·유형 | 역할극 방식은 승인됨. 번호와 역할 매핑·수신 기능을 등록, 공공기관 연락 불필요 | 실제 전화 전 |
| ClawOps 발신·Gemini 오디오·회신 지원 | 설치 SDK/공식 문서/최소 승인 통화로 실측 | M0, 최우선 기술 위험 |
| 공급자 기능 부족 | 영향·지원되는 실행 경로·변경 비용을 보고; 가짜 통화 대체나 새 공급자 몰래 도입 금지 | 발견 즉시 |
| 시연 지역·기관 | 공개 자료의 경로 완성도와 대표 요청 적합성으로 선정 | M1/M2; 서울 목록 범위 유지 |
| 운영정보 빈칸 | 현실 사업 절차에 맞는 구성 조건과 내부 근거 관리, 전면은 알아보기 행동 | 데이터 통합 전 |
| KRDS·프론트 결과 | 지정 저장소 필수, Claude 설계/구현/검증, Codex API/통합 | Claude와 통합 전 |
| 시험 부재·통신 장애 | 수신자 준비·사전 왕복 시험·같은 빌드 녹화 | M4/M5 |
| 시간 부족 | 중요도는 덱/제안서·전화·프론트 유지, 순서·대안·영향 보고 | 발견 즉시; 무단 기능 삭제 금지 |

장점은 공통 데이터와 기존 전화/저장 기반을 재사용해 핵심 경험에 집중하는 것이다. 한계는 자동 운영·기관 행정 실행·장기 인증을 제공하지 않는다는 점이며 Future로 연결한다. 시험 통화 환경과 실제 기관 협력을 구분하고, 공개 데이터가 부족하면 수집 범위를 정확히 남겨 정책 요청으로 연결한다.

## 11 전체 설계 연결

| 전체 설계 영역 | MVP에서 구현 | 이후 위치 |
|---|---|---|
| 주인공·입구·대시보드·대표·네 사업 | 유지, 담당자 중심·전화 입구 | Future 1~3/8 |
| 기억·본인 확인·보호자 | 현재 요청 저장, 시험 연락처 등록 | Future F1 |
| 전화·회신·부재 | 실제 왕복, 수동 재시도 | Future F2 |
| 담당자 인계 | 확인·정정·중단·재시도 | Future F3 |
| 신청·예약·취소 | 문의·조건 확인·구체적 신청 안내 | Future F4 |
| 데이터·출처·갱신 | 공식 데이터/현실적 구성, 내부 근거 저장 | Future F5 |
| 정책·효과·운영 | 제안서와 측정 설계 | Future F6 |

이번 계획은 해커톤 제품의 실제 작동과 제출물 완성을 목표로 한다. Future의 미결정 운영 파라미터를 MVP의 선행조건으로 끌어오지 않는다. 계획 완료·구현 완료·실제 전화 통과·제출물 완료를 별도로 보고한다.
